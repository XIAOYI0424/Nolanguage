# 《Nolanguage 大型项目环境与包管理》方案评审

> 评审日期 2026-10-18（HEAD `08a0455`）  
> 评审对象：三层模型（L1 工具链 / L2 项目环境 / L3 依赖）+ `script-host` 契约 + 四个 WS kind + UI。
> 评审依据：HEAD `08a0455` 实读 `src/runtimes/script-host.ts`、`src/panel/WorkspaceService.ts`、`src/langs/discover.ts`、`src/langs/manifest.ts`、`src/panel/server.ts`。

## 一、总体结论

**方向正确，可以按这个定位做**：Nolanguage 是"环境的感知者与调度者"，不重造 venv/nvm，不解析锁文件，环境放 `data/<id>/env/`，不进 `builtin/`。这三条与现有架构（插件只读、data 可写、零第三方依赖）完全一致。

**但方案里有 6 处与当前代码不符**，直接照抄会写不出可运行的代码。下面逐条给出证据和修正。

---

## 二、必须修正的 6 处

### 2.1 `script-host` 不是 ESM 模块契约，是"程序 + 行 JSON 协议"

方案里的 `runtime.js` 写的是：

```js
export async function envStatus({ workdir }, ctx) { ... }
export async function prepare({ workdir, force }, ctx) { ... }
```

**当前实现不是这样。** `src/runtimes/script-host.ts`：

- 子进程是 `node runtime.js`，**不是** `import()` 一个模块；
- 父进程往 stdin 写一行 `{ op: 'run', code, file, mode, sessionId, sessionDir, dataDir, timeoutMs }`；
- 子进程往 stdout 写行 JSON：`{ t: 'out', s, text }` / `{ t: 'exit', code }`；
- 非 JSON 行被当作普通输出。

所以 `runtime.js` 是一个**读 stdin、写 stdout 的程序**，不是导出函数的模块。方案里的 `ScriptHostModule` 接口、`ctx.exec`、`ctx.fs`、`ctx.progress`、`ctx.isCancelled` **都不存在**。

**修正**：把契约改成"新增 `op`"，而不是"新增导出"。

```
→  { op: 'prepare', requestId, languageId, workdir, dataDir, envName?, force?, timeoutMs }
←  { t: 'progress', phase, message, percent?, current?, total? }   (0..n 行)
←  { t: 'result', ok, state, envDir?, packageCount?, error? }
←  { t: 'exit', code }

→  { op: 'envStatus', requestId, workdir, dataDir, envName? }
←  { t: 'result', state, envDir?, packageCount?, reason? }

→  { op: 'envRemove', requestId, dataDir, envName? }
←  { t: 'result', ok }

→  { op: 'listDependencies', requestId, workdir, dataDir, envName? }
←  { t: 'result', items: [{ name, version }] }
```

`runtime.js` 的主循环按 `op` 分支：

```js
// runtime.js（程序，不是模块）
let buf = '';
process.stdin.on('data', (c) => {
  buf += c;
  let nl;
  while ((nl = buf.indexOf('\n')) >= 0) {
    const req = JSON.parse(buf.slice(0, nl));
    buf = buf.slice(nl + 1);
    if (req.op === 'prepare') void prepare(req);
    else if (req.op === 'envStatus') void envStatus(req);
    else if (req.op === 'run') void run(req);
  }
});

function progress(phase, message, percent) {
  process.stdout.write(JSON.stringify({ t: 'progress', phase, message, percent }) + '\n');
}
```

`ctx.exec` / `ctx.fs` 不需要宿主提供：子进程本身就能 `require('node:child_process')` / `node:fs`。方案里的 `PrepareContext` 应改成**插件自己实现的一个小工具模块**，宿主只提供 `dataDir/workdir/platform/timeoutMs` 四个入参。

**代价**：`ScriptHostRunner` 加 `prepare()` / `envStatus()` / `envRemove()` / `listDependencies()` 四个方法（各 spawn 一次、各解析 `t:'progress'`/`t:'result'`），约 150 行。

### 2.2 `WorkspaceService` 没有 `dataDir` / `workspaceRoot` / `runner.module`

方案的 `prepareEnvironment` 写的是：

```ts
const slot = this.requireSlot(languageId);
const runner = slot.runner;
if (!(runner instanceof ScriptHostRunner) || !runner.module.prepare) ...
const ctx = createPrepareContext({
  dataDir: join(this.dataDir, languageId),
  workdir: this.workspaceRoot,
  ...
});
```

实际字段（`src/panel/WorkspaceService.ts`）：

- `requireSlot(id)` ✅ 存在（`run()` 里就用）；
- `this.dataDir` ❌ 不存在；每个 slot 的数据目录是 `await this.registry.ensureDataDir(manifest.id)`（`hostContext()` 里调用）；
- `this.workspaceRoot` ❌ 不存在；根目录是私有 `rootDir`（`opts.workspaceDir` 或默认 temp），另有 `rootDir()` getter；
- `runner.module` ❌ 不存在；`ScriptHostRunner` 没有 `module` 字段。

**修正**：

```ts
async prepareEnvironment(
  id: LanguageId,
  opts: { envName?: string; force?: boolean },
  onProgress: (p: EnvProgress) => void,
  signal?: AbortSignal,
): Promise<EnvStatus> {
  const slot = this.requireSlot(id);
  if (!(slot.runner instanceof ScriptHostRunner)) {
    throw new Error(`"${id}" does not support environment preparation`);
  }
  const dataDir = await this.registry.ensureDataDir(slot.manifest.id);
  return slot.runner.prepare(
    { workdir: this.rootDir, dataDir, envName: opts.envName ?? 'default', force: opts.force },
    onProgress,
    signal,
  );
}
```

### 2.3 `manifest.toolchain` 不存在；工具链发现走 `run.discovery`

方案在 manifest 顶层加了 `toolchain.discovery`。当前 `LanguageManifest` **没有** `toolchain` 字段；`WorkspaceService.resolveToolchain()` 读的是 `manifest.run?.discovery`，`lsp.discovery` 是另一套（LSP 自己的发现）。

**修正（推荐）**：不要新增第二套发现路径。把 `versionFiles` 加到现有的 `BinaryDiscoverySpec`：

```ts
export interface VersionFileSpec {
  /** 相对项目根的文件名。 */
  path: string;
  /** plain | json | toml（toml 先只支持 requires-python 的浅解析）。 */
  format: 'plain' | 'json' | 'toml';
  /** json/toml 取值路径，如 engines.node / project.requires-python。 */
  key?: string;
}

export interface BinaryDiscoverySpec {
  commands?: string[];
  envVars?: string[];
  knownPaths?: string[];
  /** 新增：先读版本声明，再决定 knownPaths 里的版本目录。 */
  versionFiles?: VersionFileSpec[];
}
```

`run.discovery` 和 `lsp.discovery` 都自动获得 `versionFiles`，零新字段。如果坚持要顶层 `toolchain`，`resolveToolchain` 就要改成"`manifest.toolchain.discovery` 优先，回落 `run.discovery`"，这是第二处真相，不推荐。

### 2.4 `knownPaths` 不支持 glob

方案的例子是 `~/.pyenv/versions/*/bin/python3`。当前 `discover.ts` 只做 `~` 展开 + `existsSync` 精确路径，**没有 `*` 展开**。

**修正**：加一个 20 行的 `expandGlob()`（只支持单段 `*`，不支持 `**`）：

```ts
function expandGlob(pattern: string): string[] {
  const p = expandPath(pattern);
  const parts = p.split(/[\\/]/);
  const star = parts.findIndex((s) => s.includes('*'));
  if (star < 0) return [p];
  const base = parts.slice(0, star).join(sep) || sep;
  const tail = parts.slice(star + 1);
  const re = new RegExp('^' + parts[star].replace(/[.+^${}()|[\]\\]/g, '\\$&').replace(/\*/g, '.*') + '$');
  try {
    return readdirSync(base).filter((n) => re.test(n)).map((n) => join(base, n, ...tail));
  } catch { return []; }
}
```

然后 `discoverBinary` 对每个 `knownPaths` 展开、逐个 `existsSync`。

### 2.5 `versionFiles` 的 TOML 解析需要额外决定

`pyproject.toml` 的 `project.requires-python` 是 TOML。项目零第三方依赖，不能引 `toml` 包。

**修正（推荐）**：v1 只支持 `plain`（`.python-version`、`.nvmrc`、`go.mod` 的 `go 1.22` 行）和 `json`（`package.json` 的 `engines.node`）；TOML 先用一个**只认 `requires-python` 的正则**，不写通用 TOML 解析器。在 manifest 里注明 `format: 'toml'` 只支持这个键。

### 2.6 `envCancel` 需要真实的中断机制

方案说"插件通过 `ctx.isCancelled()` 感知"，但当前子进程没有取消通道。两条路：

- **v1（推荐）**：宿主 `envCancel` 直接 `killTree(child.pid)`（`src/desktop/session.ts` 已有 `killTree`），子进程连同 `pip` 一起结束；`prepare` 的 Promise 以 `{ ok: false, error: 'cancelled' }` 收尾。
- **v2**：stdin 写 `{ op: 'cancel', requestId }`，插件在主循环里检查；更优雅，但要插件配合。

v1 零插件改动，先做。

## 三、协议与集成的正确落点

### 3.1 四个 WS kind（与现有 `server.ts` 一致）

`server.ts` 的 `switch (msg.kind)` 已经有 `run/runOut/runResult`，照同样模式加：

| kind | 方向 | 说明 |
|---|---|---|
| `envStatus` | 请求-响应 | 返回 `{ kind:'envStatusResult', state, envDir?, packageCount?, lastError? }` |
| `envPrepare` | 请求 + 推送 | 先回 `envStarted`，再流式 `envProgress`，最后 `envResult` |
| `envCancel` | 请求 | 宿主 `killTree` 子进程 |
| `envProgress` | 推送 | `{ kind:'envProgress', requestId, phase, message, percent?, current?, total? }` |

**注意**：方案里 `envStatus` 直接回 `{ state, ... }`，但现有协议是"请求 kind 与响应 kind 分开"（`run` → `runResult`）。建议统一为 `envStatusResult` / `envResult`，避免页面把请求当响应。

### 3.2 超时与资源

- `script-host` 默认 `timeoutMs = 15_000`；`prepare` 必须单独传 **10–15 分钟**（`pip install` 可能很久），否则会被默认超时杀掉。
- RSS watchdog 监控的是 `runtime.js` 子进程（RSS 很小），`pip` 是它的孙进程，不会被误杀；但 `killTree` 取消时要连 `pip` 一起杀。
- `pip install` 需要网络；应用是离线优先，UI 必须有 `offline` / `network-error` 状态，不能静默卡住。

### 3.3 并发与幂等

- 同一 `languageId` 同时两次 `envPrepare`：建议宿主加**每语言一把串行锁**（或直接拒绝第二次，返回"正在准备中"）。方案只提了 hash 幂等，没提并发。
- marker 文件 `data/<id>/env/<name>/.prepared.json` 记录 `depHash` / `packageCount` / `preparedAt`；`force` 跳过 hash 比较。
- `envRemove` 删除 `env/<name>`，保留 marker 之外的数据（`keepData` 语义）。

### 3.4 安全（方案未覆盖）

`prepare` 会执行 `pip install` / `npm ci`，即**从公网下载并执行第三方代码**。建议：

- 只在 `trust.sandbox !== 'none'` 的插件上允许 `prepare`；
- UI 首次提示里明确"将执行 `pip install -r requirements.txt`，从 PyPI 下载"；
- 不自动运行，必须用户点击（方案已经这么定了，很好）。

## 五、方案里值得保留的好点

- 三层模型与"只感知/只调度"的定位；
- 显式创建（不隐式跑 `pip install`）；
- hash 幂等 + `force` 重试；
- 环境目录放 `data/<id>/env/`、不进 `builtin/`；
- `runtime.js` 承担每语言差异，引擎不出现语言分支；
- `phase` 枚举与流式进度。

## 六、方案里建议删掉/后置的点

- `PrepareContext` 里的 `fs` / `exec` / `isCancelled`：宿主不提供，插件自己用 Node API；`isCancelled` 用 `killTree` 代替。
- `ScriptHostModule` 的 ESM 导出形态：改成 `op` 分支。
- `manifest.toolchain` 顶层块：改成复用 `BinaryDiscoverySpec.versionFiles`。
- TOML 通用解析：v1 只认 `requires-python`。
- Java/Node 的 `runtime.js` 与依赖树 UI：P5–P7，不要和 P0–P3 混在一起。
