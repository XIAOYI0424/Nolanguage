# Nolanguage 实际功能测试方案

> 方案日期：2026-11-25
> 代码基线：`package.json` 当前版本 0.7.24；功能边界与验证入口以本方案编写时工作区中的源码为准。
> 方案属性：面向当前实现的可执行测试设计，不代表本方案中的所有测试已经执行。

## 1. 目标与原则

本方案不把“页面能打开”当作功能通过，而按真实链路验证：**用户动作 / 面板协议 → handler → WorkspaceService / Runtime / 插件 → 外部进程或文件系统 → 回执和界面状态**。覆盖成功路径、拒绝路径、取消/超时、资源边界、打包路径与用户项目保护。

测试证据分三类，报告中必须区分：

1. **自动化已有**：仓库中已有对应测试代码或验证套件。
2. **建议补充**：代码提供功能，但当前测试清单未证明该场景已被自动覆盖；实现测试后才能标为自动化通过。
3. **人工验收**：需要安装版 UI、真实桌面交互或人工确认，不得用静态检查替代。

## 3. 测试环境与数据隔离

### 3.1 环境

- Windows 10/11；记录系统版本、CPU/内存、Node 版本、WebView2/Edge 版本。
- 源码回归在仓库根目录执行；安装版验收使用安装路径下的 `Nolanguage.exe`，记录文件版本/哈希。
- Python、Go、Node、Java、gopls、jdtls 等不是一律必需。逐项记录发现到的可执行路径和版本；缺失时记为 `SKIP（缺少前置工具）`，不能算通过。
- 若脚本依赖 `jsdom`、打包 exe、网络或外部语言服务，确认其前置条件后再执行对应套件。

### 3.2 项目数据保护规则

所有会写工作区的测试必须使用每次唯一的临时副本/夹具，并在开始前证明夹具路径不等于源项目路径。预置测试文件、坏包、符号链接、故障注入文件只能放在临时目录。

对必须保持只读的真实项目（例如 `D:\15936\Documents\NeroSama`）：

- 允许：用被测 IDE 的 Open Folder 打开；`fsList`、`fsRead`、解释器候选列表、只输出信息的内存运行代码。
- 禁止：在该项目下执行 `fsWrite/fsCreate/fsRename/fsDelete`、批量替换、`envCreate`、包安装、模板生成、Git commit、会产生缓存/编译文件的项目构建或测试。
- 回归套件 `npm run verify:workspace-env` 当前默认目标是 NeroSama，且会运行 `dependencyInstall`，默认安装 `fastapi>=0.115` 到项目环境；**不得对真实 NeroSama 原样运行**。仅在完整副本或专门临时项目上设置 `NLG_TARGET_DIR` 后运行。
- `npm run verify:ide` 的运行脚本会在临时 workspace 创建虚拟环境；清理受安全策略阻止时停止并记录，不要用宽泛删除命令绕过。
- 以文件数、相对路径、大小、SHA-256 清单对比前后状态；只对比读不代表允许偷偷写，运行前后的证据都要保留在测试报告目录（仓库 `.tmp/` 或测试产物目录，不在目标项目内）。

## 4. 分层测试门禁

### Gate A：快速提交门禁

```text
npm run typecheck
npm run typecheck:scripts
npm test
npm run verify:pure
```

目的：类型、纯函数、协议/架构/文档合同和无外部服务的回归。每条命令须记录 exit code；0/0 或被过滤为空的测试不算通过。

### Gate B：真实服务集成

```text
npm run verify
```

目的：通过 `scripts/verify-all.mjs` 执行注册的服务、运行时、协议、语言插件和真实进程套件。逐套件记录 PASS/FAIL/SKIP，不只抄总数。工具缺失或 exe 不存在产生的 SKIP 必须列出。

需重点人工单独复跑的真实接口：

```text
npm run verify:stage2
npm run verify:ide
npm run verify:ui
npm run verify:workspace-env
npm run verify:lsp-manager
npm run verify:lsp-protocol
npm run verify:lsp-semantics
npm run verify:transport
```

`verify:workspace-env` 的安全前提见 §3.2；命令本身会对目标项目环境安装包，不因它是测试脚本就视作只读。

### Gate C：打包与安装版

源码回归通过后，使用项目定义的 `npm run build:all` 构建；再运行：

```text
npm run verify:sidecar
npm run verify:smoke
npm run verify:mcp-exe
npm run ci:install-smoke
```

安装冒烟会安装/卸载测试产物并触碰本机安装状态，只能在确认脚本会备份/还原注册表和 receipt 的受控 Windows 测试机上运行。安装版验收还要从实际安装目录启动应用并确认版本握手命中同一构建，不能仅验证仓库内 `dist/Nolanguage.exe`。

### Gate D：人工 UI 与目标项目只读验收

用安装版实际 UI 做“打开目标文件夹 → 展开树 → 只读打开文件 → 查看解释器候选 → 运行不写盘的短代码”，检查运行输出、目标 interpreter 路径、窗格/快捷键反馈。测试代码只能执行内存计算和标准输出，不 import 会写缓存的第三方包、不调用项目服务、不创建文件。结束后执行清单/哈希对比，差异必须为零。

## 6. 回归、证据与通过标准

### 6.1 每轮记录字段

- 测试轮次、日期、执行人、机器/OS、应用版本与 exe SHA-256。
- 测试命令或 UI 操作步骤、目标环境路径、测试夹具位置。
- 每个用例状态：PASS / FAIL / SKIP / NOT RUN；失败要含首个失败帧、请求 kind/reqId、stderr、退出码和复现步骤。
- 可选依赖的名称/版本/查找路径；因缺失跳过的用例单列。
- 临时夹具创建与清理结果；目标项目测试前后文件数、路径、大小、哈希差异。
- 产物位置和 sidecar 校验结果；安装/卸载是否完成以及用户配置是否恢复。

### 6.2 通过条件

1. Gate A 所有必需项退出码为 0；没有空选择、0/0 或隐式跳过。
2. Gate B 每个失败都已修复并复跑；SKIP 仅限事先声明的可选工具/外部前置条件，并保留清单。
3. 安全用例证明越权路径、危险输入、失败回滚和取消路径符合预期；不能只证明正常路径。
4. 安装版 Smoke / MCP exe / sidecar 版本一致；release gate 仍需干净工作树和符合流程的 tag，测试通过不等于已发布。
5. 只读真实项目的前后差异为零。任何差异都要停止后续测试，先查明是否为测试引入，不能自动清理来掩盖证据。

## 7. 当前应优先补强的测试缺口

基于当前验证结构，建议按下面顺序把建议场景加入可重复自动化测试：

1. **协议 payload 合同**：对常见消息做必填字段、类型、reqId 回传、非法字段边界断言；现有 `verify-protocol.ts` 主要核对消息名是否在登记表和两侧处理器中出现。
2. **安全目标副作用矩阵**：对 `runConfigsSave/Delete`、`projectsDetect`、`gitStatus/gitCommit`、`draft*`、`sandbox*` 等协议路径分别证明目标根、写入范围、错误回执；仅登记消息不代表覆盖行为。
3. **真实项目只读 smoke 专用脚本**：只做 `openFolder/fsList/fsRead/interpreters` 和只输出 Python 运行，不调用 `dependencyInstall/envCreate`；测试结束自动生成源文件哈希差异报告。
4. **模板端到端快照**：以 manifest 实际模板为依据，对 Python/Go/Java 项目生成结果做文件集合、内容和命令配置断言。
5. **安装版桌面交互**：自动化 shell/DOM 测试之外，定期人工确认 native folder picker、菜单焦点、安装/卸载和 Edge/WebView 启动行为。

所有建议补强项在实现测试并接入 `scripts/verify-all.mjs` 或相应 npm script 前，状态必须标为“建议补充”，不能报告为已通过。
