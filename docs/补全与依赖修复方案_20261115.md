# 补全与依赖：修复方案 + 性能影响

日期：2026-11-15 · 版本 0.7.23 · 依据：`docs/评估_20261115.md` 的实测结论

三处缺口，按「改动面 ÷ 收益」排序。每一项都给出性能影响，因为这三处都在**输入路径**上——那是唯一不能靠「慢一点无所谓」糊弄的地方。

---

## 一、补全项被丢弃的三个字段

### 现状

`src/panel/handlers/languages.ts:84`

```ts
items: items.slice(0, 100).map((i) => ({ label: i.label, kind: i.kind, detail: i.detail }))
```

`insertText` / `textEdit` / `documentation` / `sortText` / `filterText` 全部丢弃。后果：接受一个函数补全只插入裸名字，服务端排序失效，文档不显示。

### 方案

分两步，因为两者的性能性质完全不同。

**A. 立即做——短字段**（改动约 10 行）

```ts
items.slice(0, 100).map((i) => ({
  label: i.label,
  kind: i.kind,
  detail: i.detail,
  insertText: i.insertText,          // 服务端给的插入文本（常含括号与占位符）
  sortText: i.sortText,              // 服务端排序权重
  filterText: i.filterText,          // 模糊匹配用的键
}))
```

客户端 `20-editor.js` 的 `cmpAccept` 改为：优先用 `insertText`，没有才用 `label`；列表排序优先 `sortText` 再 `label`。

验收：装 pyright 后，补全一个函数应插入 `get(url, timeout=)` 这类带括号的形式，光标落在括号内。

**B. 随后做——文档按需加载**（改动约 40 行）

不在补全帧里塞 `documentation`，而是实现 `completionItem/resolve`：列表只发短字段，用户用方向键选中某一项时，再为该条请求一次详情。

需要新增：`LspClient.resolveCompletionItem(item)`、帧 `completionItemDetail`、客户端在选中变化时发请求并缓存（按 `label` 键，同一会话内不重复请求）。

验收：上下移动选中项时右侧出现文档；同一项重复选中不重复请求。

### 性能影响

| 项 | 数据 |
|---|---|
| 当前补全帧 | **1505 字节 / 32 项**（实测，内置服务） |
| A 方案后 | 约 **+15%**（`insertText`/`sortText` 都是短字符串）→ 约 1.7 KB |
| B 方案后 | 帧回到 1.5 KB 量级；每次选中变化 **+1 次 RPC** |
| RPC 往返基准 | **中位 2.2 ms**（实测，1 ms 轮询） |
| 若改为内联文档 | pyright 规模（100 项 × 约 300 字符）≈ **30 KB/帧**，每次输入都发 |

**结论**：A 无感知代价。B 的代价是「每按一次方向键 +2.2 ms」，可接受；内联文档则不行——输入路径上每帧 30 KB 会在慢机器上造成可感的卡顿，而且 99% 的文档用户根本没看。**这也是为什么 B 必须用 resolve 而不是内联。**

## 二、`textDocument/signatureHelp`（参数提示）

### 现状

`grep "'textDocument/" src/lsp/*.ts` 只有 completion / hover / diagnostic / definition / references / rename / codeAction / didOpen / didChange。**没有 signatureHelp**。装任何服务都没有参数提示。

### 方案

1. `LspClient.signatureHelp(uri, position)` → 返回 `{ signatures: [...], activeParameter }`，走和 `nav()` 相同的四态（未声明 / 未实现 / 错误 / 有值）。
2. 帧 `signatureResult`，带 `unsupported`。
3. 客户端：在 `onCodeKeyDown` 里对 `(` 和 `,` 触发；结果渲染成一个**贴在光标上方的单行浮层**（不是列表，不需要键盘导航）。
4. 编辑器失焦 / 光标移出括号 / 输入 `)` 时关闭。

验收：`requests.get(` 之后出现 `get(url, params=None, **kwargs)` 并高亮当前参数；按 `,` 高亮推进到下一个参数。

### 性能影响

| 项 | 数据 |
|---|---|
| 触发频率 | 只在 `(` 与 `,` 上，**不是每次按键** |
| 单次成本 | 1 次 RPC（2.2 ms 基准）+ 服务端计算 |
| 服务端计算 | pyright 未安装，**无法实测**；按同类实现估 30–150 ms |
| 帧大小 | 一条签名约 200–500 字节 |

**结论**：触发稀疏，单次成本可接受。但**服务端那 30–150 ms 需要在 UI 上有兜底**——浮层必须在结果到达前不占位、到达后若光标已移开则丢弃（沿用 Markdown 预览那套 `requestId` 丢弃过期响应的做法）。

**唯一需要节流的地方**：连打 `,,,` 会发三次请求。做法是 150 ms 去抖 + 只保留最后一次的 `requestId`。

## 三、依赖管理

### 现状

`src/` 里 `pip install` / `npm install` / `go get` / `requirements.txt` / `poetry` **零命中**。产品不知道项目装了什么包。

### 方案

**这不是一个 LSP 功能，是一个产品功能。** 分三层：

1. **读**（低成本，先做）
   - 按语言 manifest 声明「依赖清单文件」：Python `requirements.txt` / `pyproject.toml`，Go `go.mod`，JS `package.json`。
   - 解析出 `{ name, version }` 列表，在插件页或新的「依赖」页展示。
   - 未知包（`import requests` 但清单里没有）不报错，只标注「未声明」。

2. **装**（中成本）
   - 提供「安装」动作，走对应工具链：`python -m pip install <pkg>` / `go get` / `npm install`。
   - **必须异步 + 流式输出**，因为这是秒级到分钟级的操作，不能阻塞面板。
   - 复用现有 `termExec` 的流式通道，不新造轮子。

3. **刷**（低成本）
   - 安装完成后通知语言服务重载。LSP 有标准通知 `workspace/didChangeWatchedFiles`；服务不支持时退回重启该语言的服务。

验收：在「未声明」的包上点安装 → 进度流出 → 完成后补全能列出该包的成员。

### 性能影响

| 阶段 | 数据 | 说明 |
|---|---|---|
| 启动时解析清单 | **< 1 ms** | 三个文件都是行/JSON 解析，典型大小几十行 |
| 文件监听 | 可忽略 | 只 watch 3 个文件，不是整个项目树 |
| 安装操作 | 秒级，**网络主导** | 与产品无关；关键是异步、可取消、有进度 |
| 装完刷新 | 通知 < 1 ms；重启服务 **约 277 ms**（实测，内置 Python 服务启动） | 重启只影响该语言 |

**结论**：读与刷几乎无成本，可以随时做。真正的成本在「装」——那是网络时间，不是 CPU，所以设计重点不是省时间而是**别让 UI 卡住**。

**一个必须避免的做法**：不要在每次 `didOpen` 时去解析依赖清单来「判断包是否存在」。那会把一个 < 1 ms 的一次性成本变成每次开文件的成本，而且会让编辑延迟依赖磁盘。

## 四、总排序与风险

| 顺序 | 项 | 改动面 | 输入路径代价 | 风险 |
|---|---|---|---|---|
| 1 | 补全短字段（A） | ~10 行 | 帧 +15% | 低 |
| 2 | `signatureHelp` | ~120 行 | 每次 `(`/`,` +2.2 ms RPC | 中：服务端延迟需要去抖与过期丢弃 |
| 3 | `completionItem/resolve`（B） | ~40 行 | 每次选中 +1 RPC | 低 |
| 4 | 依赖读取与展示 | ~200 行 | 启动 < 1 ms | 低 |
| 5 | 依赖安装 | ~300 行 | 秒级，异步 | 中：进程管理与取消 |
| 6 | 装后刷新 | ~50 行 | 通知 < 1 ms / 重启 277 ms | 低 |

**共同的前置条件**：第 1、2、3 项都要求客户端能拿到「服务端到底支持什么」——那套 `declaresFeature` 已经在了，直接复用即可，不需要新机制。

**唯一的架构约束**：以上全部走 manifest + LSP 能力声明，**不允许出现按语言名分支**。`verify:langparity` 的 7 条门禁会挡住任何一处 `language === 'python'`。

## 五、实现结果（0.7.24）

六项全部落地，按上表顺序：

| 项 | 落点 | 说明 |
|---|---|---|
| 1 补全短字段 | `handlers/languages.ts` · `30-panels.js` | `insertText`/`sortText`/`filterText` 透传；客户端按 `sortText` 排序，并把 `$1`/`${1:name}` 展开成默认文本 |
| 2 `signatureHelp` | `LspClient` → `handleSignatureHelp` → `68-nav.js` | 只在 `(`/`,` 触发，150 ms 去抖，`requestId` 过期丢弃 |
| 3 `completionItem/resolve` | `resolveCompletion` → `handleCompletionResolve` → `cmpOnDetail` | 文档按需取，帧里不带 docstring；`CMP.docs` 按语言清空 |
| 4 依赖读取 | `langs/dependencies.ts` · `readDependencies` | 解析 requirements / go.mod / package.json；只读项目根，越界路径跳过 |
| 5 依赖安装 | `langs/dependencies.ts` · `installPackage` | 用 manifest 的 `install` 前缀 + 包名，`spawn` 直连（不经 shell），输出流式回传，可取消 |
| 6 装后刷新 | `WorkspaceService.restartLanguageServer` | `releaseLsp` + `ensureLsp`，只重启该语言的服务 |

界面是底部工具窗 **Packages（Alt+6）**：声明清单、未声明导入、安装输入框与输出台。命令来自清单，因此没有任何一处按语言名分支——`verify:langparity` 7/7 通过。

**新增门禁**：`tests/pure.test.ts` 的 `project dependencies` / `package install` 两组（12 条），`verify:ide` 新增 9 条端到端检查（读 package.json、未声明导入、拒绝 `-r`、取消空转）。
