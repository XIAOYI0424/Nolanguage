# Nolanguage 与 PyCharm、IntelliJ IDEA 等 IDE 的差距评估

日期：2026-11-22
代码版本：`package.json` 标记为 0.7.24
评估对象：当前工作区源码，不等同于已发布安装包

> **重要口径**：本次评估检查的是当前 checkout 中的源码。工作区已有多处未提交修改，包版本号并不能证明这些改动已经进入安装包；因此下文描述的是“源码树中已实现或尚缺的能力”，不表示发布产物已经全部具备。未在本次验证中实际运行的能力标为“源码可见 / 依赖环境”，不会写成已实测。

> **同日补充（2026-11-22，评估之后）**：以下四项在本次评估后已落地并有门禁覆盖，下文对应的“尚缺/占位”描述按评估当时的源码为准。
> - 测试树：`Alt+5` Tests 窗口，`testRun` / `testStart` / `testOut` / `testCase` / `testResult` / `testCancel`，单测级过滤与失败跳转，失败项并入 Problems；覆盖 `verify:go`、`verify:ide`、`verify:ui`。
> - Inlay Hints：`textDocument/inlayHint` 全链路（LSP 归一化 → 调度预算 → 客户端视口请求 → CodeMirror 行内 widget），覆盖 `verify:lsp-protocol`、`verify:ui`、单测。
> - 插件索引：`/plugins` 与 Tauri 对话框都能搜索远程索引；下载前强制校验 `sha256`，缺失/不匹配即拒绝安装（`--strict` 下更严）；覆盖 `verify:langcatalog`、`verify:langsource`、`verify:ui`。
> - AI 助手：面板与右侧抽屉都走真实 provider（OpenAI 兼容流式），密钥只落在 `<appData>/ai.json`，可取消、失败可读；覆盖 `verify:ai`、`verify:ui`、单测与 `docs/ai-panel-protocol.md`。

## 结论摘要

Nolanguage 已不只是静态界面样例：它有实际的项目文件树、编辑与保存、代码运行、诊断、LSP 请求、环境与依赖操作、调试/性能入口、插件化语言装配，以及一套 JetBrains 风格的桌面工作区。但它目前更准确的定位仍是：**轻量、多语言、可扩展的本地开发与执行工作台，带有 IDE 外壳**，而不是 PyCharm 或 IntelliJ IDEA 的功能等价替代品。

差距主要不是菜单和配色，而是 IDE 深度：**完整的项目/构建模型、稳定可分发的语言服务、跨文件语义重构、测试与 VCS 的日常工作流，以及真正连接模型服务的 AI 辅助**。这些功能决定了大型项目中“理解整个工程并安全修改”的能力。

### 状态标记

- **已实现**：源码中有可追踪的实现路径；不自动表示当前机器/发布包已验证。
- **部分**：可完成有限场景，或要依赖用户安装的工具/语言服务，或只实现了工作流的一部分。
- **缺失 / 占位**：未发现可用实现，或入口目前只显示提示、返回固定演示内容。
- **设计取舍**：功能边界来自当前产品架构，不等于技术上永远做不到。

## 做得较好的部分

1. **以数据驱动扩展语言能力**：`RunnerFactory` 与语言 manifest 将运行、工具链、依赖和部分 LSP 能力放在插件描述中，避免把每一种语言都写成独立 UI 分支。
2. **用户可以实际编辑项目文件**：`src/panel/FsService.ts`、`src/ui/client/30-panels.js` 有文件树、缓冲区、保存确认、磁盘重载、脏状态及恢复草稿相关流程。
3. **LSP 请求面较完整**：客户端与 `WorkspaceService` / handlers 有补全、诊断、导航、参数提示、格式化、折叠等连接；这提供了继续利用语言服务器的基础。
4. **本地执行和环境操作是产品的一等能力**：运行、终端、项目解释器、依赖管理、运行配置不只是静态菜单。
5. **MCP 与性能观测形成差异化底座**：内置 MCP 面板、Perf/Logs/Profile 等可以服务于工具扩展和 Nolanguage 自身内核诊断；但它们不能替代缺失的代码智能、AI provider 或完整 VCS。

## 当前源码中值得先处理的问题

- F6 与 Ctrl+F6 的完整语义重构当前尚未实现；本次已将快捷键和菜单改为明确提示“不支持”，并加了无运行时异常的回归检查。提示不应被误读成 Move 或 Change Signature 已完成。
- Refactor 菜单中 Extract Method、Extract Variable、Extract Constant、Move、Change Signature 仍有提示型/占位行为。界面名称存在不代表重构已实现。
- Cross-file rename 和 Code Action 的客户端只安全应用当前缓冲区的编辑；多文件编辑若不能完整落盘就必须拒绝或明示，不能报告成项目级安全重构。
- 右侧 Assistant 输入目前是预设回复，不会访问模型；左侧 AI 面板与状态栏编码/EOL 项应标注为尚未接通，避免被误认为可用功能。
- 不应把标签关闭操作、Markdown 预览拖拽或项目面板 resize 等局部交互描述成通用多编辑器分屏、完整布局系统或全功能 IDE 设置。

## 与主流 IDE 的差距优先级建议

### P0：可信度和核心编辑闭环

1. 修复所有已展示但无目标函数的快捷键；菜单标题、快捷键、实际行为和测试统一。
2. 明确区分“本地演示/无语言服务/语言服务不支持/请求失败”，并避免搜索、AI、重构入口显示成功但实际不工作。
3. 设计可验证的 WorkspaceEdit 应用流程：多文件读取、冲突/版本校验、预览、原子或可回滚写入；完成前继续把跨文件重命名标为部分支持。

### P1：专业日常工作流

1. 建立按 manifest/测试框架驱动的 Test Explorer、发现、过滤、重跑失败测试与结果导航。
2. 给 Git 增加逐文件 diff、stage/unstage、branch/history/blame 等操作，同时保持未跟踪文件的提交安全。
3. 连接可配置 AI provider，并把活动文件/选区/项目上下文作为有权限边界的请求；清晰处理无密钥、失败、取消与隐私。
4. 接通状态栏编码与换行设置、右侧面板 resize、标签固定和编辑器分屏等用户可见的高频交互。

### P2：工程级理解与生态

1. 对接构建系统和多模块项目模型；不要只凭当前文件缓冲区模拟“全项目支持”。
2. 补充语义导入整理、更多安全重构、Inlay Hints、语言检查配置和测试覆盖率映射。
3. 建立可持续的插件目录、版本兼容策略、包完整性校验/签名信任、来源管理与更新治理。
4. 再评估远程/容器、多根工作区和扩展市场；这些投入应与轻量、零 Node 运行时依赖的产品目标一起权衡。
