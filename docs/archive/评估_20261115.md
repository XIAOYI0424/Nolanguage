# 逐语言能力评估：Nolanguage 0.7.24 与主流 IDE 的差距

日期：2026-11-15 · 版本 0.7.24 · 方法：读 manifest 声明 + 打包 exe 实测 + 检查本机工具链

> **一个必须先说清的前提**：语言服务**一个都没有随产品分发**。本机只有两个是手动装进 `.tmp/langdeps` 的（tsserver、rust-analyzer），
> 其余全部缺失：pyright / gopls / marksman / clangd / jdtls / debugpy / dlv / codelldb。
> 所以每张表都分两列：**「声明」= manifest 里写了**，**「本机可用」= 实际能跑**。二者的差距就是这个产品当前的真实体验。
> 这不是产品缺陷，是分发选择——但它决定了「开箱即用」能到什么程度：**八种语言里只有两种开箱就有智能，而那两种是我手动装的。**

## 逐语言差距

### Python · 对标 PyCharm

**当前实际能做什么**：跑代码（306ms）、覆盖率（stdlib trace）、31 项补全（无成员解析）、lint 级诊断、五个导航能力、参数提示、依赖读写装、3 个解释器候选（venv/conda/pyenv）、SDK 名称匹配。语言服务走内置 stub，因为 pyright 没装。

| 维度 | Nolanguage | PyCharm | 差距性质 |
|---|---|---|---|
| 类型检查 | **只有 lint 级**：语法、未定义名、未用导入。`x: int = "str"`、参数个数/类型、缺 return、不存在属性——**全部漏报** | 自研引擎，完整类型推断 | **引擎缺失**：需要 pyright，且不能只做兜底 |
| 成员补全 | ❌ `json.` 与 `requests.` 返回**同一批**内置名（无成员解析、无库内省、无跨文件） | 完整 | 引擎缺失（装 pyright 即解决） |
| 自动导入 | ❌ 只有「删除未使用 import」 | ✅ | 引擎缺失 |
| 未安装包的诊断 | ❌ 零诊断（Packages 窗能列出「未声明」，但诊断流里没有） | ✅ | 产品级，需自建 import 解析 |
| 重构 | 仅**符号重命名**（LSP rename） | 提取方法/变量、内联、改签名、移动 | 未实现 |
| 快速修复 | ✅ 走 LSP `codeAction`（stub 只给「删除未用 import」） | 大量 intent | 引擎缺失 |
| 调试 | 声明 debugpy，**未装即无** | 内置 pydevd，开箱可用 | **工具链缺口**（不是能力缺口） |
| 测试 | ❌ 无 test 模式 | pytest/unittest 集成、测试树 | 未实现 |
| 覆盖率 | ✅ 可用（trace 模块，439ms） | 内置，可视化 | 接近 |
| 性能剖析 | 声明 cProfile，需 `pstats` 解析 | 内置 profiler + 火焰图 | 部分 |
| 环境管理 | 只读发现（3 个候选） | venv/conda/pipenv/poetry + 创建/切换 UI | 只读 vs 可管理 |
| 依赖管理 | ✅ 读 + 装 + 装后重启 | 完整（解析、锁文件、版本冲突、虚拟环境联动） | **半程**：无 resolver、无锁文件、无版本冲突提示 |
| VCS | status + commit | diff/blame/分支/冲突解决/shelve | 差距大 |
| 生态 | MCP 客户端 | 数据库、Jupyter、科学模式、远程解释器、框架支持 | 定位不同 |

**一句话**：Python 是四种语言里体验最完整的（唯一有覆盖率、唯一有兜底服务、唯一有依赖安装闭环），但**类型检查缺失**让它离「IDE」还有一段距离——而这恰好是 PyCharm 的核心价值。

### Go · 对标 GoLand

**当前实际能做什么**：跑代码（3.2s）、`go test`、go.mod 脚手架、go/bin 与 scoop 路径发现、pprof 声明、依赖 `go get`。

| 维度 | Nolanguage | GoLand | 差距性质 |
|---|---|---|---|
| 语言服务 | 声明 gopls，**未装即无**；无兜底 | gopls 内置 | **工具链缺口**：Go 没有「stub 兜底」的可能，没 gopls 就是零智能 |
| 诊断/补全 | ❌ | 完整 | 同上 |
| 调试 | 声明 delve，未装即无 | Delve 内置 | 工具链缺口 |
| 测试 | ✅ `go test`（唯一有 test 模式的语言） | 表驱动、benchmark、子测试、测试树 | **部分**：能跑，无树、无单测粒度、无 benchmark |
| 覆盖率 | ❌ **未声明**（而 `go test -cover` 极便宜） | 内置 | **低成本缺口，值得补** |
| 性能剖析 | 声明 pprof | 内置 | 部分 |
| 重构 | 仅符号重命名 | 重命名、提取、内联、实现接口 | 引擎缺失 |
| 代码生成 | 无 | 结构体标签、接口实现、测试骨架 | 未实现 |

**一句话**：Go 是「声明最完整、实际最空」的一个——debug/profiler/scaffold/test 都声明了，但没装 dlv/gopls 就只剩跑和测。**覆盖率是四种语言里最容易补的**（`go test -cover` 原生支持），目前却偏偏没声明。

### JavaScript · 对标 WebStorm / VS Code

**当前实际能做什么**：跑代码 **2ms 且零安装**（内联 VM，全产品最快的一条路径）、nvm/volta 路径发现、`npm install` 依赖安装。

| 维度 | Nolanguage | WebStorm / VS Code | 差距性质 |
|---|---|---|---|
| 语言服务 | 声明 tsserver，未装即无 | 内置 TS 引擎 | 工具链缺口 |
| 诊断/补全 | ❌ | 完整 + 类型推断 | 同上 |
| 调试 | **未声明** | inspector 内置 | **能力缺口**（连声明都没有） |
| 性能剖析 | **未声明** | CPU profile / heap snapshot | 能力缺口 |
| 测试 | ❌ | Jest/Mocha/Vitest 集成 | 未实现 |
| 框架支持 | 无 | React/Vue/Angular/Svelte | 未实现 |
| 包管理 UI | ✅ 装（`npm install`），无脚本列表 | npm/pnpm/yarn UI + scripts | 部分 |
| 运行 | ✅ **2ms**，零依赖 | 需配置 Node SDK | **反超** |

**一句话**：JS 的运行是全产品最强的（零安装、2ms），但**调试和剖析连声明都没有**。Node 自带 `--cpu-prof` 与 inspector 协议，补这两项的技术门槛比 Go/Python 都低。

### Markdown · 对标 Typora / Obsidian / VS Code

**当前实际能做什么**：渲染预览（65ms）、大纲、面包屑、`contributes.completion`、链接与图片的安全过滤。

| 维度 | Nolanguage | 对标产品 | 差距性质 |
|---|---|---|---|
| 预览 | ✅ 内置，24%–64% 可拖动分栏 | 实时双栏（Typora 所见即所得） | 接近 |
| 大纲 | ✅ Structure 窗复用 headings | 侧边大纲、可拖拽排序 | 接近 |
| 语言服务 | 声明 marksman，未装即无 | marksman 提供定义/引用/符号 | 工具链缺口 |
| 链接检查 | 无（依赖 marksman） | Obsidian 全库断链检查 | 未实现 |
| 表格/公式/图表 | 未实现（Mermaid、KaTeX 均无） | Typora/Obsidian 支持 | 未实现 |
| 导出 | 无 | PDF/HTML/Word | 未实现 |
| 锚点跳转 | 部分：标题有 slug id，但预览内点击不跳 | 完整 | 未实现 |

**一句话**：预览与大纲够用，缺的是**链接完整性**、**图表/公式**和**导出**——这三项都不依赖外部工具链，纯属未实现。

## C++ / C · 对标 CLion

**当前实际能做什么**：`g++ -std=c++17` / `gcc -std=c11` 编译后运行（实测 `cpp 42` / `c 42`）、语法高亮、五个导航能力（需 clangd）、codelldb 调试声明、test 模式（同一次编译）。

| 维度 | Nolanguage | CLion | 差距性质 |
|---|---|---|---|
| 项目模型 | **单文件**：编译当前缓冲区，产物落在临时目录 | CMake 工程模型：target、编译数据库、多目标 | **架构差距**：产品没有「工程」概念，只有「缓冲区」 |
| 构建 | 一条 `gcc/g++` 命令 | CMake / Makefile / Ninja，增量构建 | 未实现 |
| 语言服务 | clangd（未装即无） | clangd 内置 + 编译数据库 | 工具链缺口 + 需要 `compile_commands.json` |
| 调试 | codelldb（未装即无） | LLDB/GDB 内置，可视化 | 工具链缺口 |
| 重构 | 仅符号重命名 | 提取/内联/改签名/生成 | 引擎缺失 |

| 静态分析 | 无（clangd 有诊断时算有） | clang-tidy 集成 | 未实现 |
| 覆盖率 | ❌ | gcov/lcov 集成 | 未声明 |
| 内存/线程检查 | 无 | Valgrind / Sanitizer 集成 | 未实现 |

**一句话**：C/C++ 能编译能跑，但**没有工程模型**——CLion 的核心是「理解整个 CMake 工程」，我们理解的是「当前这一个文件」。

## 跨语言共有的差距

| # | 差距 | 影响 | 补齐难度 |
|---|---|---|---|
| 1 | **工具链全需用户自装** | 开箱体验 = 只有运行、预览、依赖安装；四种语言都没有智能 | 小（改分发）：可打包或首启引导 |
| 2 | **无测试运行器**（仅 Go 有 `go test` 一条命令） | 三种语言不能跑单测，没有测试树、没有单测粒度 | 中：按 manifest 声明命令模板 |
| 3 | **重构只有符号重命名** | 无提取方法/变量、内联、改签名、移动 | 大：依赖引擎 |
| 4 | **VCS 只有 status + commit** | 无 diff 视图、blame、分支操作、冲突解决 | 大，且价值密度低 |
| 5 | **无多光标、无编辑器分屏** | 单编辑器 + Markdown 分栏，批量编辑靠手 | 中：CodeMirror 支持，未接线 |
| 6 | **无远程/容器/多根工作区** | 只能编辑本机一个目录 | 大，且与「85 MB 单文件」的定位冲突 |
| 7 | **无 AI 补全**；侧栏的 AI Assistant 窗**只有输入框和 Ask 按钮，没有接线**（点了没反应） | 有 MCP 客户端（能调外部工具），没有 inline completion；AI 窗是空壳，比没有更糟 | 中：需接模型，与零依赖冲突；**空壳应先删掉或标注「未配置」** |
| 8 | **没有工程模型**：一个语言 = 一个缓冲区，编译/运行当前这一个文件 | 多文件、多模块、跨文件依赖全部不成立；C++/Rust/Java 因此「只能写单文件程序」 | **大，且是架构级**：需要引入 workspace/project 概念 |
| 9 | **不接构建系统**：CMake / Make / Cargo 工作区 / Maven / Gradle 一个都没接 | 编译型语言无法使用第三方依赖，无法增量构建，无法多目标 | 大：每种构建系统一个适配层 |
| 10 | **无格式化**：`textDocument/formatting` 在客户端根本没有实现（`src/lsp` 里零命中），rustfmt / gofmt / black / clang-format 也都未接线 | 保存即格式化这类习惯无法建立 | 中：一个 LSP 请求 + 应用 `TextEdit` + 一个快捷键，八种语言同时受益 |

## 可安装的示例插件（`examples/`）

产品内置四种语言，但插件层能装的远不止四种。仓库里带四个可安装的示例，都走同一条 `nlg lang add`：

| 插件 | 扩展名 | 编译器 | 语言服务 | 本机实测 |
|---|---|---|---|---|
| `examples/cpp@1.0.0` | cpp cc cxx c++ hpp hh hxx h | g++ / clang++ / c++ | clangd | 编译并跑出 `cpp 42`；clangd 缺失时导航如实报错 |
| `examples/c@1.0.0` | c | gcc / clang / cc | clangd | `c 42` |

装完四种后同一个工作区里有八种语言。这说明「多语言」不是四种，而是「插件写了多少种」——差距表里的每一条语言能力，对示例插件同样成立：装上服务就有智能，没装就如实说缺什么。

## 性能影响排序（实现这些功能要付多少运行时代价）

| 排名 | 功能 | 性能代价 | 依据 |
|---|---|---|---|
| **1** | **打包四种语言服务** | **+630 MB 常驻**、冷诊断 +2.5–20 s、每语言一个子进程 | manifest 的 `memoryHint`：pyright **380 MB**、tsserver **150 MB**、gopls **80 MB**、marksman **20 MB**；gopls 冷诊断 **20 s** |
| 2 | 调试适配器（debugpy / dlv） | 按需一个进程，非常驻；debugpy 约 60–120 MB | 只在点「调试」时启动 |
| 3 | 测试运行器 | 每次运行一个进程，与「运行文件」同量级 | 无常驻 |
| 4 | Go 覆盖率 | 一次 `go test -cover` ≈ 一次完整构建 | 编译型固有 |

| 7 | 多光标 / 分屏 | 零后端代价 | 纯客户端 |

## 添加一个新包之后：各语言的补全与周边能力

先说实测结论：**补全不看上下文**。同一份代码里，`json.` 和 `requests.` 返回的是**完全相同**的结果——这是内置 stub 的能力边界，不是客户端的问题。

### 实测（内置 Python 服务，打包 exe）

| 场景 | 诊断 | 补全 |
|---|---|---|
| `import json` + `json.loads("{}")` | 无 | **31 项**，全是 `Exception` / `False` / `None` / `TypeError` 这类内置名 |
| `import requests`（**未安装**） | **无**——不检查包是否存在 | 31 项，与上面一模一样 |
| 光标在 `json.` 之后 | `SyntaxError: invalid syntax` | 30 项，同上 |
| 光标在 `requests.` 之后 | `SyntaxError: invalid syntax` | 30 项，同上 |

补全实现（`pyrightServer.py` 的 `completion()`）是：固定内置名列表 + 当前文件里定义的名字 + **import 进来的名字（扁平地混在一起）**。没有成员解析，没有库内省，没有跨文件。

### 逐语言矩阵

`✅` 有 · `❌` 无 · `—` 不适用。第二列是「装上真语言服务之后」——请求面已经是通用的，装上就能用。

| 能力 | Python（内置 stub） | Python（装 pyright） | Go（gopls） | JS（tsserver） | Markdown |
|---|---|---|---|---|---|
| 包名补全（打 `import req` 提示已装包） | ❌ | ✅ | ✅ | ✅ | — |
| **成员补全**（`requests.` → `get`/`post`…） | ❌ 与 `json.` 结果相同 | ✅ | ✅ | ✅ | — |
| 参数提示（signature help） | ✅ **0.7.24**（stub 支持同文件与内置） | ✅ | ✅ | ✅ | — |
| 跳转到库源码（site-packages / node_modules） | ❌ 仅同文件 | ✅ | ✅ | ✅ | — |
| 自动导入 | ❌ 只有「删除未使用 import」 | ✅ | ✅ | ✅ | — |
| 未安装包的诊断 | ❌ 零诊断 | ✅ | ✅ | ✅ | — |
| 补全插入可用调用（`insertText` + 片段） | ✅ **0.7.24** | ✅ | ✅ | ✅ | — |
| 补全项按需文档（`resolve`） | ✅ **0.7.24**（内置名有 docstring） | ✅ | ✅ | ✅ | — |
| 依赖管理界面（装/升/删） | ✅ **0.7.24**：装（`pip install`）+ 读 + 装后重启 | ✅ | ✅ | ✅ | — |

## 建议顺序（按「单位投入的体验提升」排序）

1. **按需下载语言服务与调试适配器**（pyright / gopls / tsserver / marksman / clangd / jdtls / debugpy / dlv / codelldb）。这是**唯一一处「不写新功能、只改分发」就能让八种语言同时从「记事本」跨到「有智能」的改动**。代价是常驻内存与冷诊断延迟——按需下载比内联进 85 MB 单文件更合适，实测 rust-analyzer 冷启动要几秒才能出第一条补全。
1.5. **工程模型**（多文件 / 多模块）。C++/Rust/Java 的差距不在这张表的任何一格，而在「一个语言只有一个缓冲区」。这是唯一一条能同时解开 CMake、Cargo、Maven 三条线的改动。
2. **Go 覆盖率**（`go test -cover`，几乎零成本，Go 用户期望很高）。
3. **测试运行器**（按 manifest 声明命令模板；Go 已有 `go test` 可作第一条）。
4. **JS 调试与剖析**（Node 原生 `--cpu-prof` + inspector，零第三方依赖）。
5. **依赖管理的后半程**（版本解析、锁文件、冲突提示），现在只有读/装/刷。
6. Markdown 断链检查 + 导出（纯本地实现，无外部依赖）。
