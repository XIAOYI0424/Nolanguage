# 逐语言能力评估：Nolanguage 0.7.23 与主流 IDE 的差距

日期：2026-11-15 · 版本 0.7.23 · 方法：读 manifest 声明 + 打包 exe 实测 + 检查本机工具链

> **一个必须先说清的前提**：本机 **一个语言服务、一个调试适配器都没装**（pyright / gopls / tsserver / marksman / debugpy / dlv 全部缺失）。
> 所以下表分两列：**「声明」= manifest 里写了**，**「本机可用」= 实际能跑**。二者差距就是这个产品当前的真实体验。

## Python · 对标 PyCharm

**当前实际能做什么**：跑代码（306ms）、覆盖率（stdlib trace）、32 项补全、lint 级诊断、3 个解释器候选（含 venv/conda/pyenv）、SDK 名称匹配（PyCharm 迁移用）。语言服务走内置 357 行 stub，因为 pyright 没装。

| 维度 | Nolanguage | PyCharm | 差距性质 |
|---|---|---|---|
| 类型检查 | **只有 lint 级**：语法、未定义名、未用导入。`x: int = "str"`、参数个数/类型、缺 return、不存在属性——**全部漏报** | 自研引擎，完整类型推断与检查 | **引擎缺失**：需要 pyright 或等价物，且不能只做兜底 |
| 导航 | 无 | 定义/引用/符号/继承层级 | 客户端未实现 |
| 重构 | 仅文件重命名 | 重命名符号、提取方法/变量、内联、改签名、移动 | 未实现 |
| 快速修复 | 无 | 大量 intent（补 import、转 f-string、加类型注解…） | 未实现 |
| 调试 | 声明 debugpy，**未装即无** | 内置 pydevd，开箱可用 | **工具链缺口**（不是能力缺口） |
| 测试 | 无 | pytest/unittest 集成，单测/整文件/整目录运行，测试树 | 未实现 |
| 覆盖率 | ✅ 可用（trace 模块） | 内置，可视化 | 接近 |
| 性能剖析 | 声明 cProfile，需 `pstats` 解析 | 内置 profiler + 火焰图 | 部分 |
| 环境管理 | 只读发现（3 个候选） | venv/conda/pipenv/poetry 全支持 + 创建/切换 UI | 只读 vs 可管理 |
| VCS | status + commit | diff/blame/分支/冲突解决/shelve | 差距大 |
| 生态 | MCP 客户端 | 数据库、Jupyter、科学模式、远程解释器、Django/Flask 支持 | 定位不同 |

**一句话**：Python 是四种语言里体验最完整的（唯一有覆盖率、唯一有兜底服务），但**类型检查缺失**让它离「IDE」还有一段距离——而这恰好是 PyCharm 的核心价值。

## Go · 对标 GoLand

**当前实际能做什么**：跑代码（3.2s，走 `directory-session` + go.mod 脚手架）、go/bin 与 scoop 路径发现、pprof 声明。

| 维度 | Nolanguage | GoLand | 差距性质 |
|---|---|---|---|
| 语言服务 | 声明 gopls，**未装即无**；无兜底 | gopls 内置 | **工具链缺口**：Go 没有「stub 兜底」的可能，没 gopls 就是零智能 |
| 诊断/补全 | 无 | 完整 | 同上 |
| 调试 | 声明 delve（`dlv`），未装即无 | Delve 内置，开箱可用 | 工具链缺口 |
| 测试 | 无 | 表驱动测试、benchmark、子测试、覆盖率一体化 | 未实现 |
| 覆盖率 | ❌ 未声明（而 Go 原生 `-cover` 极便宜） | 内置 | **低成本缺口，值得补** |
| 性能剖析 | 声明 pprof | 内置 pprof 集成 | 部分 |
| 重构 | 无 | 重命名、提取、内联、实现接口 | 未实现 |
| 项目模型 | go.mod 脚手架 | 完整模块管理 UI | 部分 |
| 代码生成 | 无 | 结构体标签、接口实现、测试骨架 | 未实现 |

**一句话**：Go 是「声明最完整、实际最空」的一个——debug/profiler/scaffold 都声明了，但没装 dlv/gopls 就全空。Go 的覆盖率是四种语言里最容易补的（`go test -cover` 原生支持），目前却偏偏没声明。

**当前实际能做什么**：跑代码 **2ms 且零安装**（内联 VM，这是全产品最快的一条路径）、nvm/volta 路径发现。

## 四语言共有的差距（与语言无关）

| # | 差距 | 影响 | 补齐难度 |
|---|---|---|---|
| 1 | **五个导航能力客户端未实现** | 四种语言全部「能看不能改」 | 中：LSP 客户端 + 5 个请求 + UI |
| 2 | **无测试运行器** | 四种语言都不能跑单测 | 中：按 manifest 声明 |
| 3 | **VCS 只有 status + commit** | 无 diff/blame/分支 | 大，且价值密度低 |
| 4 | **工具链全需用户自装** | 开箱体验 = 只有运行和预览 | 小：可打包或首启引导 |
| 5 | **无重构能力** | 无重命名/提取/内联 | 大：依赖导航层先落地 |

## 建议顺序（按「单位投入的体验提升」排序）

1. **打包语言服务与调试适配器**（pyright / gopls / tsserver / marksman / debugpy / dlv）。这是**唯一一处「不写新功能、只改分发」就能让四种语言同时从「记事本」跨到「有智能」的改动**。
2. **补五个导航能力**（客户端层）。装不装服务是第二层，先让请求发得出去。
3. **Go 加覆盖率**（`go test -cover`，几乎零成本，且 Go 用户对此期望很高）。
4. **JS 加调试与剖析**（Node 原生 `--cpu-prof` + inspector，零第三方依赖）。
5. **测试运行器**（按 manifest 声明命令模板）。
6. Markdown 断链检查 + 导出（纯本地实现，无外部依赖）。

## 性能影响排序（按「实现后对性能的代价」从大到小）

先给结论：**性能代价最大的那一项，恰好也是体验收益最大的那一项**（打包语言服务）。这不是巧合——语言服务本身就是重型常驻进程。

| 排名 | 差距 | 性能代价（实测/声明依据） | 说明 |
|---|---|---|---|
| **1** | **打包/启用四种语言服务** | **+630 MB 常驻**、冷诊断 +2.5–20 s、每语言一个子进程 | manifest 自己声明的 `memoryHint`：pyright **380 MB**、tsserver **150 MB**、gopls **80 MB**、marksman **20 MB**。gopls 的 `coldDiagnosticsTimeoutMs` 是 **20 000 ms** |
| 2 | 调试适配器（debugpy / dlv） | 按需一个进程，非常驻；debugpy 约 60–120 MB | 只在点「调试」时启动，不影响冷启动 |
| 3 | 五个导航能力（定义/引用/重命名/修复/符号） | **≈0 常驻**；`workspace/symbol` 首次全库索引有一次扫描 | 复用已有 LSP 连接，只增加请求。索引成本随文件数线性 |
| 4 | 测试运行器 | 每次运行一个进程，与「运行文件」同量级 | 无常驻开销 |
| 5 | Go 覆盖率 | 一次 `go test -cover` ≈ 一次完整构建 | 编译型语言的固有成本 |
| 6 | JS 调试 / 剖析 | `--cpu-prof` 落盘，几 MB | 零常驻 |
| 7 | Markdown 断链检查 | 纯本地扫描，随文件数线性 | 可忽略 |

**这张表推翻了上一版的排序**：按「单位投入的体验提升」，打包语言服务排第一；但按「性能代价」，它也排第一。两者并不矛盾，而是同一个决定的两面——**值不值得为 630 MB 换四种语言的智能**。如果答案为是，正确做法不是「全打包」，而是：

- 按语言**按需启动**（现在只有 python 是 `eager`）；
- 首次打开某语言文件时才拉服务，而不是启动就全上；
- 用 `memoryHint` 做预算拒绝（manifest 已经声明了，但没有被用来限制）。

## 现有性能开销实测（零工具链安装状态）

### 冷启动 1896 ms 的去向

用产品自己的 `boot.log` 阶段打点（`--no-open`，端口就绪为止）：

| 阶段 | 时间点 | 增量 | 归因 |
|---|---|---|---|
| 进程启动 → `boot` | 0 ms | — | — |
| `boot` → `server-starting` | 29 ms | **29 ms** | SEA 引导 |
| `server-starting` → `Kernel started` | 773 ms | **744 ms** | **`import('../panel/server.js')` 的模块图加载 + 内核构造**（最大单块，未再细分） |
| → `Extension host ready` | 999 ms | **226 ms** | 每个扩展一个子进程（`demo.hello` 也起了进程） |
| → `Baseline captured` | 1012 ms | 13 ms | — |
| → LSP `initialize` 完成 | 1474 ms | **462 ms** | 起 Python stub 服务；`initialize` RPC 本身 **183 ms**，超过 60 ms 阈值（产品自己打了 WARN） |
| → `Workspace ready` | 1513 ms | 39 ms | — |
| → `Dev server ready` | 1539 ms | 26 ms | — |
| **合计到 `/health`** | **1896 ms** | | |

**三个可优化点**：744 ms 的模块图加载、226 ms 的扩展子进程、183 ms 的 LSP 握手。

### 稳态开销

| 指标 | 实测 | 说明 |
|---|---|---|
| RPC 往返（`ping`） | **0.5–15.9 ms，中位 2.2 ms** | 之前的「62 ms」是**测试客户端的 50 ms 轮询**，不是产品 |
| `fsList`（36 项） | 7.7 ms | |
| `fsWrite` / `fsRead` | 1.9 / 1.3 ms | |
| `check` 诊断 | 2.3 ms | stub 服务 |
| `complete` / `hover` | 1.3 / 1.1 ms | |
| `mdRender` | 2.7 ms | |
| `gitStatus` | **76.8 ms** | **唯一真慢的常规操作**：每次 spawn 一个 `git` 进程 |
| `run` JavaScript | **2 ms** | 内联 VM，`durationMs` 由产品自己上报 |
| `run` Python | ~300 ms | 进程启动 + REPL 会话 |
| `run` Go | ~3.2 s | 编译，不可避免 |
| 内存 | **133 MB**（2 个进程：75 + 58）+ 23 MB（Python LSP）= **~156 MB** | 零工具链状态 |
| 首页 | 971 KB / **5 ms** | 单页应用，含 CodeMirror |

### 值得动手的三件事（按性价比）

1. **`gitStatus` 77 ms** —— 唯一一个「每次都要等」的常规操作，缓存或改增量即可，代价最小。
2. **744 ms 的模块图加载** —— 把 debugtool / mcp / profiler / dap 等改成按需 `import`，冷启动有机会砍掉一半。
3. **扩展宿主 226 ms** —— 内置扩展（demo.hello / demo.faulty）没必要各起一个进程，可同进程或延迟到首次使用。

> 这三项都不需要新增功能，纯属现有开销。

## 关于测量方法的一个教训

初版报告里的「62 ms」全部来自测试客户端的 `waitFor()` 每 **50 ms** 轮询一次——量到的是轮询粒度，不是产品延迟。改成 1 ms 轮询后，同一批操作是 1–8 ms。

**任何用轮询等待测出来的延迟都要先扣掉轮询粒度**，否则会系统性地把快的东西报慢，并据此做出错误的优化决策。
