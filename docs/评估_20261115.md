# 逐语言能力评估：Nolanguage 0.7.23 与主流 IDE 的差距

日期：2026-11-15 · 版本 0.7.23 · 方法：读 manifest 声明 + 打包 exe 实测 + 检查本机工具链

> **一个必须先说清的前提**：本机 **一个语言服务、一个调试适配器都没装**（pyright / gopls / tsserver / marksman / debugpy / dlv 全部缺失）。
> 所以下表分两列：**「声明」= manifest 里写了**，**「本机可用」= 实际能跑**。二者差距就是这个产品当前的真实体验。

## Python · 对标 PyCharm

**当前实际能做什么**：跑代码（306ms）、覆盖率（stdlib trace）、32 项补全、lint 级诊断、3 个解释器候选（含 venv/conda/pyenv）、SDK 名称匹配（PyCharm 迁移用）。语言服务走内置 357 行 stub，因为 pyright 没装。

| 维度 | Nolanguage | PyCharm | 差距性质 |
|---|---|---|---|
| 类型检查 | **只有 lint 级**：语法、未定义名、未用导入。`x: int = "str"`、参数个数/类型、缺 return、不存在属性——**全部漏报** | 自研引擎，完整类型推断与检查 | **引擎缺失**：需要 pyright 或等价物，且不能只做兜底 |
| 导航 | 无 | 定义/引用/符号/继承层级 | 客户端未实现 |
| 重构 | 仅文件重命名 | 重命名符号、提取方法/变量、内联、改签名、移动 | 未实现 |
| 快速修复 | 无 | 大量 intent（补 import、转 f-string、加类型注解…） | 未实现 |
| 调试 | 声明 debugpy，**未装即无** | 内置 pydevd，开箱可用 | **工具链缺口**（不是能力缺口） |
| 测试 | 无 | pytest/unittest 集成，单测/整文件/整目录运行，测试树 | 未实现 |
| 覆盖率 | ✅ 可用（trace 模块） | 内置，可视化 | 接近 |
| 性能剖析 | 声明 cProfile，需 `pstats` 解析 | 内置 profiler + 火焰图 | 部分 |
| 环境管理 | 只读发现（3 个候选） | venv/conda/pipenv/poetry 全支持 + 创建/切换 UI | 只读 vs 可管理 |
| VCS | status + commit | diff/blame/分支/冲突解决/shelve | 差距大 |
| 生态 | MCP 客户端 | 数据库、Jupyter、科学模式、远程解释器、Django/Flask 支持 | 定位不同 |

**一句话**：Python 是四种语言里体验最完整的（唯一有覆盖率、唯一有兜底服务），但**类型检查缺失**让它离「IDE」还有一段距离——而这恰好是 PyCharm 的核心价值。

## Go · 对标 GoLand

**当前实际能做什么**：跑代码（3.2s，走 `directory-session` + go.mod 脚手架）、go/bin 与 scoop 路径发现、pprof 声明。

| 维度 | Nolanguage | GoLand | 差距性质 |
|---|---|---|---|
| 语言服务 | 声明 gopls，**未装即无**；无兜底 | gopls 内置 | **工具链缺口**：Go 没有「stub 兜底」的可能，没 gopls 就是零智能 |
| 诊断/补全 | 无 | 完整 | 同上 |
| 调试 | 声明 delve（`dlv`），未装即无 | Delve 内置，开箱可用 | 工具链缺口 |
| 测试 | 无 | 表驱动测试、benchmark、子测试、覆盖率一体化 | 未实现 |
| 覆盖率 | ❌ 未声明（而 Go 原生 `-cover` 极便宜） | 内置 | **低成本缺口，值得补** |
| 性能剖析 | 声明 pprof | 内置 pprof 集成 | 部分 |
| 重构 | 无 | 重命名、提取、内联、实现接口 | 未实现 |
| 项目模型 | go.mod 脚手架 | 完整模块管理 UI | 部分 |
| 代码生成 | 无 | 结构体标签、接口实现、测试骨架 | 未实现 |

**一句话**：Go 是「声明最完整、实际最空」的一个——debug/profiler/scaffold 都声明了，但没装 dlv/gopls 就全空。Go 的覆盖率是四种语言里最容易补的（`go test -cover` 原生支持），目前却偏偏没声明。

## JavaScript · 对标 WebStorm / VS Code

**当前实际能做什么**：跑代码 **2ms 且零安装**（内联 VM，这是全产品最快的一条路径）、nvm/volta 路径发现。

| 维度 | Nolanguage | WebStorm / VS Code | 差距性质 |
|---|---|---|---|
| 语言服务 | 声明 tsserver，未装即无 | 内置 TS 引擎 | 工具链缺口 |
| 诊断/补全 | 无 | 完整 + 类型推断 | 同上 |
| 调试 | **未声明** | Chrome/node inspector 内置 | **能力缺口**（连声明都没有） |
| 性能剖析 | **未声明** | CPU profile / heap snapshot | 能力缺口 |
| 测试 | 无 | Jest/Mocha/Vitest 集成 | 未实现 |
| 重构 | 无 | 全套 | 未实现 |
| 框架支持 | 无 | React/Vue/Angular/Svelte | 未实现 |
| 包管理 | 无 | npm/pnpm/yarn UI，脚本列表 | 未实现 |
| 运行 | ✅ **2ms**，零依赖 | 需配置 Node SDK | **反超** |

**一句话**：JS 的运行是全产品最强的（零安装、62ms），但**调试和剖析连声明都没有**。Node 自带 `--cpu-prof` 与 inspector 协议，补这两项的技术门槛比 Go/Python 都低。

## Markdown · 对标 Typora / Obsidian / VS Code

**当前实际能做什么**：渲染预览、大纲、面包屑、`contributes.completion`（语言内补全）。

| 维度 | Nolanguage | 对标产品 | 差距性质 |
|---|---|---|---|
| 预览 | ✅ 内置，65ms，24%–64% 可拖动分栏 | 实时双栏（Typora 所见即所得） | 接近 |
| 大纲 | ✅ Structure 窗复用 headings | 侧边大纲、可拖拽排序 | 接近 |
| 语言服务 | 声明 marksman，未装即无 | marksman 提供定义/引用/符号 | 工具链缺口 |
| 链接检查 | 无（依赖 marksman） | Obsidian 全库断链检查 | 未实现 |
| 表格/公式/图表 | 未验证 | Typora/Obsidian 支持 Mermaid、KaTeX | 未实现 |
| 导出 | 无 | PDF/HTML/Word | 未实现 |
| 目录/锚点跳转 | 未实现（属导航能力缺口） | 完整 | 未实现 |

**一句话**：Markdown 的预览与大纲够用，缺的是**链接完整性**和**导出**——这两项不依赖任何外部工具链，纯属未实现。

## 四语言共有的差距（与语言无关）

| # | 差距 | 影响 | 补齐难度 |
|---|---|---|---|
| 1 | **五个导航能力客户端未实现** | 四种语言全部「能看不能改」 | 中：LSP 客户端 + 5 个请求 + UI |
| 2 | **无测试运行器** | 四种语言都不能跑单测 | 中：按 manifest 声明 |
| 3 | **VCS 只有 status + commit** | 无 diff/blame/分支 | 大，且价值密度低 |
| 4 | **工具链全需用户自装** | 开箱体验 = 只有运行和预览 | 小：可打包或首启引导 |
| 5 | **无重构能力** | 无重命名/提取/内联 | 大：依赖导航层先落地 |

## 建议顺序（按「单位投入的体验提升」排序）

1. **打包语言服务与调试适配器**（pyright / gopls / tsserver / marksman / debugpy / dlv）。这是**唯一一处「不写新功能、只改分发」就能让四种语言同时从「记事本」跨到「有智能」的改动**。
2. **补五个导航能力**（客户端层）。装不装服务是第二层，先让请求发得出去。
3. **Go 加覆盖率**（`go test -cover`，几乎零成本，且 Go 用户对此期望很高）。
4. **JS 加调试与剖析**（Node 原生 `--cpu-prof` + inspector，零第三方依赖）。
5. **测试运行器**（按 manifest 声明命令模板）。
6. Markdown 断链检查 + 导出（纯本地实现，无外部依赖）。

## 这个产品反而领先的地方

| 维度 | Nolanguage | 对标 IDE |

## 性能影响排序（按「实现后对性能的代价」从大到小）

### 先修正上一版的三个错误归因

| 上一版说法 | 实测 | 结论 |
|---|---|---|
| 「744 ms 模块图加载」 | **16 ms** | 打包是**单个 1.6 MB CJS**，动态 `import()` 不省解析时间。真正的大头是 `kernel.start()` 与 workspace 初始化 |
| 「gitStatus 77 ms，每次都要等」 | 客户端只在**开面板 / 提交后 / 手动刷新**时请求 | 是按需，不是每次。且 77 ms 是 **git 进程启动地板**：`git rev-parse` 在本仓库 146–153 ms、空目录也要 134 ms。`--no-optional-locks`、`-uno` 均无改善 |
| 「扩展宿主 226 ms」 | 改懒激活后实测 **-76 ms** | 226 ms 是两个日志点之间夹了别的工作；真实成本 76 ms |

三条里只有第三条成立，且幅度是原来的三分之一。**归因错了，优化就会做错地方**——这也是为什么这一轮先加打点再动手。

### 冷启动实测（三次取中位）

| 阶段 | 改前 | 改后 | 增量 | 归因 |
|---|---|---|---|---|
| `boot` → `server-starting` | 33 ms | 36 ms | ~33 ms | SEA 引导 |
| → `server-module-loaded` | 49 ms | 52 ms | **16 ms** | 模块图（单 bundle，已内联） |
| → `kernel-started` | 373 ms | 371 ms | **~320 ms** | `correlation.prime()`（spawn git）+ SQLite 打开 + 三条 spine 安装 |
| → `server-ready` | 1022 ms | **946 ms** | **~575 ms** | LSP eager（277 ms）+ 扩展（已省 76 ms）+ slots/demo/baseline |

**总冷启动 1022 ms → 946 ms（-7.4%）**，唯一改动是 `demo.hello` 从 `onStartup` 改为按命令激活。

### 三项优化的处置

| 项 | 处置 | 依据 |
|---|---|---|
| `gitStatus` 77 ms | **不做** | 按需调用；77 ms 是 git 进程地板，无可调参数。加缓存只会引入「外部 checkout 后状态过期」的风险，换不来体感 |
| 744 ms 模块图 | **前提错误，不做** | 实测 16 ms。若要继续压启动，目标是 `kernel.start()` 的 320 ms 与 workspace 的 575 ms |
| 扩展宿主 | **已做** | `demo.hello` 改懒激活，-76 ms；打包冒烟 27/27（命令仍能跨进程跑出 987） |

### 下一步真正的启动优化目标（按收益排序）

| 目标 | 可省 | 代价 |
|---|---|---|
| `correlation.prime()` 的 git 调用改为**后台解析** | ~77 ms | 早期日志的 `gitCommit` 会是 `unknown`，需要能回填 |
| SQLite 存储改为**首次写入时打开** | 待测 | 首次写入会多一次延迟 |
| Python LSP 去掉 `eager`（改首次编辑时启动） | ~277 ms | 首次诊断要等；这是产品当初的刻意选择 |

## 按性能影响排列「功能实现」

同一张表，换成「实现这个功能会给运行时增加多少开销」——这是决定做不做的另一半依据。

| 排名 | 功能 | 性能代价 | 依据 |
|---|---|---|---|
| **1** | **打包四种语言服务** | **+630 MB 常驻**、冷诊断 +2.5–20 s、每语言一个子进程 | manifest 的 `memoryHint`：pyright **380 MB**、tsserver **150 MB**、gopls **80 MB**、marksman **20 MB**；gopls 冷诊断 **20 s** |
| 2 | 调试适配器（debugpy / dlv） | 按需一个进程，非常驻；debugpy 约 60–120 MB | 只在点「调试」时启动 |
| 3 | 测试运行器 | 每次运行一个进程，与「运行文件」同量级 | 无常驻 |
| 4 | Go 覆盖率 | 一次 `go test -cover` ≈ 一次完整构建 | 编译型固有 |
| 5 | 五个导航能力（定义/引用/重命名/修复/符号） | **≈0 常驻**，复用已有 LSP 连接 | 只有 `workspace/symbol` 首次全库索引有成本 |
| 6 | JS 调试 / 剖析 | `--cpu-prof` 落盘几 MB | 零常驻 |
| 7 | Markdown 断链检查 | 纯本地扫描，随文件数线性 | 可忽略 |

**注意第 5 名**：五个导航能力是体验差距最大的一项，但性能代价几乎为零——它只是复用已经建立的 LSP 连接。**如果先做性能预算紧张的项，这一项应该提前**。

所以三条排序轴给出的结论并不一致：

| 轴 | 第一名 |
|---|---|
| 体验收益 / 工作量 | 打包语言服务 |
| 性能代价（越大越靠前） | 打包语言服务 |
| **性能代价（越小越优先做）** | **五个导航能力** |

打包语言服务是「高收益 + 高代价」，五个导航能力是「高收益 + 零代价」——**先做后者**才是理性顺序。
