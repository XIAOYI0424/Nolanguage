# 第一部分 · 平台整体设计

## 一、平台定位

**一句话定位**：一个轻量级、协议驱动、AI 原生的统一开发平台，同时覆盖"写代码、跑代码、看文档、测性能、查日志"五条主线。

**核心特征**：

| 特征    | 含义                                               |
| ----- | ------------------------------------------------ |
| 统一    | C/C++、Python、Java、Go、C#、Markdown 在同一工作台内编辑、调试、执行 |
| 轻量    | 内核 < 5000 行，启动 < 2s，常驻内存 < 500MB                 |
| 协议驱动  | LSP / DAP / MCP / OTLP 四协议解耦，能力可插拔               |
| AI 原生 | 所有能力通过命令总线暴露为 AI Agent 可调用工具                     |
| 性能内建  | 从项目第 1 行代码开始自监测，实时可见，数据持续积累                      |
| 日志统一  | 所有来源日志共享关联骨架，与性能数据交叉查询                           |
| 文档即代码 | Markdown 代码块可直接执行、结果回填                           |

## 二、设计哲学：七条原则

| 原则          | 含义                                                |
| ----------- | ------------------------------------------------- |
| 内核做机制，扩展做策略 | 内核只管路由、生命周期、注册表；功能全部由扩展提供                         |
| 协议解耦        | LSP/DAP/MCP/OTLP 四协议代替 M×N 集成                     |
| 统一关联骨架      | 所有数据共享 traceId / gitCommit / configHash / fileUri |
| 延迟激活        | 启动只加载清单，功能按需激活                                    |
| 可禁用即零开销     | 任何扩展禁用后内核无感知                                      |
| 自监测优先       | 平台自身性能与日志是第一公民，先测自己                               |
| 开发即测量       | 开发模式下性能与日志实时可见，无需事后开启                             |

## 六、核心组件 3：编辑器与 Markdown

## 七、核心组件 4：执行平面

| 路线          | 适用               | 启动延迟   | 隔离           |
| ----------- | ---------------- | ------ | ------------ |
| 容器化沙箱 + 预热池 | 全语言、完整程序         | 90ms   | 进程 + FS + 网络 |

# 第二部分 · 性能监测（自监测优先）

## 八、性能监测的定位

**从项目第 1 行代码开始内建**，不是后期附加功能。开发模式下 100% 全量采集，实时可见，每次 commit 自动建立基线。

## 九、五维指标体系

| 维度   | 关键指标                                                  | 目标                   |
| ---- | ----------------------------------------------------- | -------------------- |
| 内核   | command.latency / event.throughput / service.activate | P95 < 10ms           |
| 扩展宿主 | rpc.roundtrip / memory.rss / crash.count              | P95 < 20ms / < 100MB |
| 语言服务 | lsp.completion / lsp.diagnostic / lsp.memory          | P95 < 100ms          |
| 编辑器  | input.latency / render.frame / scroll.jank            | P95 < 16ms           |
| 进程   | cpu.percent / memory.rss / gc.pause                   | < 5% / < 500MB       |

## 十、开发期实时机制

- **Dev Mode**：100% 采集，1Hz 推送，慢路径立即捕获
- **自动埋点**：内核自带中间件，与业务代码同步演进
- **实时聚合**：内存滑动窗口，秒级统计
- **慢路径捕获**：超过阈值自动保存完整调用树
- **自动基线**：每次 Git commit 创建基线，与上一基线对比

## 十一、统一数据模型（性能）

```typescript
interface PerfEnvelope {
  id: string; traceId?: string; parentId?: string;
  timestamp: number; duration?: number;
  resource:    { scope, languageId?, extensionId?, processId? };
  scope:       { workspaceId?, fileUri?, line?, symbol?, stack? };
  correlation: { gitCommit?, configHash?, sessionId?, benchmarkId? };
  environment: { os, arch, cpuModel, cpuCores, memoryTotal, runtimeVersion? };
}
type PerfEvent  = PerfEnvelope & { type:'event';  category; name; status };
type PerfSample = PerfEnvelope & { type:'sample'; profileType; value; stack };
type PerfMetric = PerfEnvelope & { type:'metric'; name; value; unit };
```

## 十二、归因引擎

三步归因：**CUSUM 突变检测** → **Welch t-test + Cohen's d 置信度** → **二分定位到文件/函数**。置信度 > 0.8 才告警。

## 十三、存储：冷热分离

```
热数据（内存环形缓冲 20MB）→ 温数据（SQLite 30天）→ 冷数据（Parquet）
```

# 第三部分 · 日志系统框架

## 十四、日志系统的定位与目标

日志系统与性能脊柱同级，是**平台第一阶段的横切基础设施**。

| 目标   | 含义                                                 |
| ---- | -------------------------------------------------- |
| 统一   | 六类来源（内核/扩展/语言服务/执行/用户代码/AI）共享同一数据模型                |
| 可关联  | 与 PerfEnvelope 共享 traceId / correlation，日志与性能可交叉查询 |
| 结构化  | 每条日志是结构化记录，支持字段查询                                  |
| 跨进程  | 扩展宿主、语言服务器的日志自动汇聚到内核                               |
| 低开销  | 单条写入 < 1μs，平台整体影响 < 1%                             |
| 实时可见 | 开发模式下日志实时推送到面板                                     |
| 可持久化 | 热/温/冷三级存储，支持长期检索                                   |

## 十八、日志采集器

### 18.1 内核采集器（内置，零配置）

```typescript
class KernelLogCollector {
  install(kernel: Kernel) {
    kernel.commands.use(async (cmd, args, next) => {
      const span = tracer.startSpan('command', { name: cmd });
      logger.span(span).trace(`Command ${cmd} started`);
      try {
        const result = await next(args);
        logger.span(span).trace(`Command ${cmd} done`);
        return result;
      } catch (err) {
        logger.span(span).error(`Command ${cmd} failed`, {}, err);
        throw err;
      } finally {
        span.end();
      }
    });
    // 事件总线、服务注册表同理
  }
}
```

## 十九、日志管道

### 19.1 五级处理

```
原始 LogRecord
    ↓
[1] 缓冲（无锁环形缓冲，写入 < 100ns）
    ↓
[2] 过滤（级别、组件、正则、速率）

[5] 批处理 + 背压（512 条或 1 秒刷一次）

```

### 19.3 背压控制

```typescript
class LogPipeline {
  private buffer: LogRecord[] = [];
  private backpressure = false;
  private readonly capacity = 65536;
  
  ingest(record: LogRecord) {
    if (this.backpressure && record.level < LogLevel.WARN) return;
    this.buffer.push(record);
    if (this.buffer.length >= 512) this.flush();
    if (this.buffer.length >= this.capacity) {
      this.backpressure = true;
      this.buffer = this.buffer.filter(r => r.level >= LogLevel.WARN);
      setTimeout(() => this.backpressure = false, 5000);
    }
  }
}
```

### 20.4 轮转与清理

| 数据          | 保留策略               |
| ----------- | ------------------ |
| 热内存         | 环形覆盖，永不落盘          |
| SQLite      | 30 天，超期归档为 Parquet |

```typescript
// ============ Logger Facade ============
interface Logger {
  trace(message: string, fields?: Record<string, unknown>): void;
  debug(message: string, fields?: Record<string, unknown>): void;
  info(message: string, fields?: Record<string, unknown>): void;
  warn(message: string, fields?: Record<string, unknown>): void;
  error(message: string, fields?: Record<string, unknown>, error?: Error): void;
  fatal(message: string, fields?: Record<string, unknown>, error?: Error): void;
  metric(name: string, value: number, fields?: Record<string, unknown>): void;
  audit(action: string, actor: string, target: string, result: string): void;
  withContext(ctx: Partial<LogRecord['correlation']>): Logger;
  forComponent(name: string): Logger;
  span(span: Span): Logger;
}

// ============ Kernel 装配 ============
class LogSpine {
  install(kernel: Kernel) {
    this.pipeline = new LogPipeline({...});
    this.router   = new LogRouter(DEFAULT_ROUTES);
    this.store    = new LogStore({ hot, warm, cold });
    this.hub      = new LogHub(this.pipeline, this.router, this.store);
    
    kernel.services.register('log.pipeline', () => this.pipeline, { lifecycle: 'singleton' });
    kernel.services.register('log.router',   () => this.router,   { lifecycle: 'singleton' });
    kernel.services.register('log.store',    () => this.store,    { lifecycle: 'singleton' });
    kernel.services.register('log.hub',      () => this.hub,      { lifecycle: 'singleton' });
    
    kernel.logger = new LoggerFactory(this.pipeline);
    new KernelLogCollector().install(kernel);
    kernel.rpc.on('log.batch', (batch) => this.hub.ingestFromHost('host', batch));
    this.startFlushTimer();
  }
}
```

## 三十八、核心结论

**平台本质**：把"写代码、跑代码、看文档、测性能、查日志"五条主线，通过**一套微内核 + 五类扩展点 + 四协议 + 两条脊柱（性能 + 日志）+ 一个统一关联骨架**粘合在一起。

**四个关键设计决策**：

1. **内核只做路由**：命令总线、服务注册表、事件总线三大基础设施 + 进程隔离 + 依赖注入，让扩展只声明"要什么"。
2. **协议解耦代替 M×N 集成**：LSP 解决编辑器 × 语言，DAP 解决调试 × 语言，MCP 解决 AI × 能力，OTLP 解决监测 × 后端。
3. **统一关联骨架代替统一数据形态**：`traceId / gitCommit / configHash / fileUri / sessionId` 五个 ID 贯穿性能、日志、代码位置、AI 上下文、执行结果。
4. **性能与日志双脊柱从第 1 阶段内建**：自监测优先，开发即测量，数据持续积累。

**最终目标**：

- 接入一门新语言只需 40 行声明
- 一次代码改动的性能影响，从"感觉变慢了"到"`tree-sitter.parse` 慢了 78%，commit abc1234 引入"，全程自动化
- 一次操作的问题排查，从"翻三个日志文件"到"点击 traceId 看时间轴"，日志、性能、代码位置一屏可见
- Markdown 代码块可直接执行、结果回填、AI 理解上下文
- UI 与 CLion / PyCharm 一致，所有图标为自研 SVG，不依赖 emoji 或 Unicode 符号
