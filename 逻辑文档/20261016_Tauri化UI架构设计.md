### 1.3 现状的三个结构性问题

1. **要占一个 TCP 端口**。`EADDRINUSE` 是真实故障模式（`desktop/main.ts` 的注释里专门记录了双启动导致的端口竞争）。
2. **窗口是「借来的」**。用 Edge 的 Chromium 开关拼出一个 app 窗口：独立 profile、去 sidebar/copilot、`--no-first-run`……能工作，但每次 Chromium 改开关名都要重验（`WebViewHost.ts` 头部记录了一次 `msedgewebview2.exe` 不能独立启动的踩坑）。
3. **UI 焊死在 WebSocket 上**。`pycharm-ui.ts:591` 直接 `new WebSocket(...)`；`server.ts` 直接把 `reply` 挂在 ws 连接上。换传输方式要同时改两头，且没有测试能证明「换传输不改行为」。

> 好消息：协议本身已经是干净的 `{kind, ...}` 消息路由 + `reqId` 关联 + `PanelSink.send()` 抽象。这意味着**换传输是机械的**，这是整个迁移可行的前提。

## 2. 目标架构

### 2.1 一句话

**Tauri v2 的 Rust 进程当「窗口 + 中转站」，现有 Node SEA exe 当 sidecar 子进程跑引擎，前端从 `tauri://localhost` 加载，UI→引擎走 IPC 而不是 WebSocket。**

```
┌── Nolanguage-Tauri.exe（Rust core，约几 MB）────────────────────────────┐
│                                                                          │
│  Window（WebView2，无浏览器边框）                                          │
│   └─ tauri://localhost ──► pycharm-ui.ts 的静态产物（index.html/app.js）   │
│                                                                          │
│  IPC 桥（Rust）                                                           │
│   ├─ invoke('engine_send', {msg})  ──► 写一行 JSON 到 sidecar stdin        │
│   └─ sidecar stdout 每行 JSON      ──► emit('engine_message', msg)        │
│                                                                          │
│  sidecar: Nolanguage-x86_64-pc-windows-msvc.exe（Node SEA，引擎原样）      │
│   内核 / WorkspaceService / LSP / ExecService / FsService / ExtensionHost │
└──────────────────────────────────────────────────────────────────────────┘
       没有 HTTP 服务，没有端口，没有 WebSocket。
```

### 2.2 为什么这样切

| 决策 | 理由 |
|---|---|
| **引擎保持 Node，不重写成 Rust** | 引擎是六层（kernel/workspace/lsp/exec/extensions/store），依赖 `node:child_process` 起 LSP、`node:vm` 沙箱、SEA 打包。重写等于推倒已建成的全部阶段，且要重写全部 17 个验证套件。 |
| **引擎跑成 sidecar，不跑在 webview 里** | WebView 里没有 `child_process`/`fs`/`net`。任何碰文件系统、进程、语言服务器的代码都必须在 webview 之外。Sidecar 正是 Tauri 给这条路的官方机制。 |
| **Rust 只做「壳 + 中转」** | Rust 侧不需要懂协议：它只认「一行 JSON 进、一行 JSON 出」。所有语义判断继续留在 TS 的 `switch (msg.kind)` 里 —— 这也是测试能继续复用的原因。 |
| **保留 `npm run ide` 的 HTTP 模式** | 没有 Rust 工具链的机器、CI、以及 `verify-*` 套件全都依赖它。Tauri 是新增的一种宿主，不是替换。 |

### 2.3 明确不推荐的做法

**不要**让 Tauri 窗口直接加载 `http://127.0.0.1:<port>`。Tauri v2 默认不允许远端 http 内容（要额外开 capability），而且端口竞争、防火墙弹窗、以及「先起服务再开窗口」的时序问题原样保留 —— 那就白迁移了。

## 4. 传输层设计

### 4.1 后端：把 `reply` 从 WebSocket 上摘下来

```ts
// src/panel/Transport.ts（新增）
export interface Transport {
  /** 发给这一个客户端；与 PanelSink.send 同语义，绝不抛异常。 */
  send(payload: PanelServerMessage): void;
  /** 收到客户端消息；`onMessage` 抛出的异常只影响该连接。 */
  onMessage(handler: (msg: Record<string, unknown>) => void): void;
  close(): void;
}

// WsTransport：今天的 WebSocketServer 路径（dev / npm run ide 保留）
// StdioTransport：Tauri sidecar 路径 —— 就是读写 stdio
export class StdioTransport implements Transport {
  private buf = '';
  constructor(private io = { in: process.stdin, out: process.stdout }) {}
  send(p: PanelServerMessage): void {
    try { this.io.out.write(JSON.stringify(p) + '\n'); } catch { /* 管道断了 */ }
  }
  onMessage(h: (m: Record<string, unknown>) => void): void {
    this.io.in.setEncoding('utf8');
    this.io.in.on('data', (chunk: string) => {
      this.buf += chunk;
      let nl: number;
      while ((nl = this.buf.indexOf('\n')) >= 0) {
        const line = this.buf.slice(0, nl).trim();
        this.buf = this.buf.slice(nl + 1);
        if (!line) continue;
        try { h(JSON.parse(line)); } catch { this.send({ kind: 'error', message: 'invalid JSON' }); }
      }
    });
  }
  close(): void { /* 由进程退出负责 */ }
}
```

`server.ts` 里的连接装配随之参数化：

```ts
// 现在：hub.addClient({ id, send: reply })
// 之后：
const transport = process.argv.includes('--panel-stdio') ? new StdioTransport() : await new WsTransport(...);
hub.addClient({ id: hub.allocateClientId(), send: (p) => transport.send(p) });
transport.onMessage((msg) => route(msg, (p) => transport.send(p)));  // route 就是 280 行那个 switch
```

> `route()` 需要从闭包里提出来。这是 `server.ts` 唯一需要动的地方，且**行为不变** —— 可以用一个 Node 端测试同时驱动 Ws 与 Stdio 两种 transport 跑同一批消息断言。

### 4.2 前端：一个 `BRIDGE`，两种实现

`pycharm-ui.ts:591` 现在长这样：

```js
var ws = new WebSocket((location.protocol === 'https:' ? 'wss://' : 'ws://') + location.host + '/');
ws.onopen = function () { ws.send(JSON.stringify({ kind: 'listExtensions' })); bootProject(); };
ws.onmessage = function (ev) { handle(JSON.parse(ev.data)); };
```

改成（其余代码一行不动，`handle()` / `send()` 全部照旧）：

```js
// ---------- transport bridge ----------
// 同一个页面跑在两种宿主里：Node 起服务时用 WebSocket，Tauri 里走 IPC。
// 判据只有一个 —— Tauri 注入了 window.__TAURI__。
var BRIDGE = (function () {
  if (window.__TAURI__) {
    var t = window.__TAURI__;
    return {
      send: function (msg) { t.invoke('engine_send', { msg: msg }); },
      onMessage: function (fn) { t.event.listen('engine_message', function (e) { fn(e.payload); }); },
      onOpen: function (fn) { fn(); }              // IPC 常连，无需握手
    };
  }
  var ws = new WebSocket((location.protocol === 'https:' ? 'wss://' : 'ws://') + location.host + '/');
  return {
    send: function (msg) { ws.send(JSON.stringify(msg)); },
    onMessage: function (fn) { ws.onmessage = function (ev) { fn(JSON.parse(ev.data)); }; },
    onOpen: function (fn) { ws.onopen = fn; }
  };
})();
BRIDGE.onMessage(handle);
BRIDGE.onOpen(function () { BRIDGE.send({ kind: 'listExtensions' }); bootProject(); });
```

注意 `ws.onclose` 现在被吞掉了（「keep shell usable offline」）。IPC 模式下没有「断开」概念，但 sidecar 可能崩 —— 用 `engine_exit` 事件补上这个语义，toast 提示而不是静默。

### 4.3 Rust 中转（`src-tauri/src/engine.rs`，约 120 行）

```rust
#[tauri::command]
fn engine_send(app: tauri::AppHandle, msg: serde_json::Value) -> Result<(), String> {
    let line = serde_json::to_string(&msg).map_err(|e| e.to_string())? + "\n";
    app.state::<Engine>().write(line)
}

pub struct Engine { stdin: Mutex<ChildStdin>, child: Mutex<Child> }

// 起 sidecar，一个 reader 线程按行读 stdout，逐行 emit 给 webview
pub fn spawn(app: &AppHandle) -> Result<Engine, String> {
    let shell = app.shell();
    let (mut rx, child) = shell.sidecar("Nolanguage")?.args(["--panel-stdio"]).spawn()?;
    let stdin = child.stdin().take().ok_or("no stdin")?;
    let app2 = app.clone();
    tauri::async_runtime::spawn(async move {
        use tauri::async_runtime::ReceiverExt;
        while let Some(Ok(bytes)) = rx.next().await {
            for line in String::from_utf8_lossy(&bytes).lines() {
                if let Ok(v) = serde_json::from_str::<serde_json::Value>(line) {
                    let _ = app2.emit("engine_message", v);
                }
            }
        }
        let _ = app2.emit("engine_exit", serde_json::json!({ "code": null }));
    });
    Ok(Engine { stdin: Mutex::new(stdin), child: Mutex::new(child) })
}
```

Rust 侧**不解析任何 kind**，只做字节搬运 —— 这意味着引擎的所有语义与测试都留在 TS。

### 4.4 流式消息的两种选择

| 消息 | 方案 A（先做，够用） | 方案 B（后续优化） |
|---|---|---|
| `runOut`（stdout 流，可能高频） | `emit('engine_message', msg)` 复用 kind 字段 | `tauri::ipc::Channel`：`invoke('run', {channel})`，Rust 只转发不落 JSON |
| `log` / `metrics` / `slow` | 同上 | Channel 或按 level 分流到不同事件名 |
| `termExec` / `termInput`（交互式 stdio） | `invoke('term_exec')` + `invoke('term_input', {text})`，输出走 emit | Channel 双向 |
| `fsChanged` / `diagnostics` / `extension` | emit | — |

建议先全走 A：一条代码路径、一套测试；等有实测数据再对 `runOut` 单独优化。过早上 Channel 会让 Rust 侧开始懂协议。

## 6. 测试策略（迁移不改行为的证据）

这个项目的护城河是 17 个套件 / 963 条断言。Tauri 化必须让它们继续有效，而且**要多跑一遍**。

`scripts/verify-pycharm.ts` 现在用 `mountPage(markup, seed)` 注入 `FakeSocket`。加一个 `FakeTauri`：

```ts
class FakeTauri {
  static invokes: Record<string, unknown>[] = [];
  static listeners: Record<string, Array<(p: unknown) => void>> = {};
  static install(w: any): void {
    FakeTauri.invokes = [];
    FakeTauri.listeners = {};
    w.__TAURI__ = {
      invoke: (cmd: string, args: Record<string, unknown>) => { FakeTauri.invokes.push({ cmd, args }); return Promise.resolve(); },
      event: { listen: (name: string, fn: (p: unknown) => void) => {
        (FakeTauri.listeners[name] ??= []).push(fn); return Promise.resolve(() => undefined); } },
    };
  }
  static emit(name: string, payload: unknown): void {
    (FakeTauri.listeners[name] ?? []).forEach((fn) => fn({ payload, event: name }));
  }
}
```

于是同一批 UI 断言能跑两遍：

```
PASS  bridge: ws 模式 —— 打开文件 / 高亮 / Run 发 run / 恢复会话 …
PASS  bridge: tauri 模式 —— 同样的断言，send 走 invoke('engine_send')，消息走 emit('engine_message')
```

`mountPage` 需要多一个参数：`mountPage(markup, seed?, bridge?: 'ws' | 'tauri')`。这与之前给恢复路径加 `seed` 是同一个套路。

Node 侧同理：给 `Transport` 写一个测试，用同一批 `{kind:…}` 消息分别驱动 `WsTransport`（起真实 ws server）和 `StdioTransport`（用 Duplex pair 假管道），断言返回的消息序列逐条相等。

|---|---|---|
| `--app=<url>` 无边框 | `app.windows[0]` + `decorations` 设置 | 外壳自己画了标题栏和菜单；若用原生边框就把 `decorations` 留默认 |
| 独立 `--user-data-dir` | Tauri 的 webview 数据目录本来就在 app data 下 | 不再需要 `webViewProfileDir()` 那一套路径推导 |
| `--no-first-run` / `--no-default-browser-check` / `--disable-features=…` | 不需要 | 这些都是在"借用浏览器"时才要的补丁 |
| `--window-size=` | `width` / `height` / `minWidth` / `minHeight` | — |
| 无单实例保护（现在能起第二个，然后端口竞争） | `tauri-plugin-single-instance` | 顺带修掉 `desktop/main.ts` 注释里那个 EADDRINUSE 故障模式 |
| 窗口位置/大小不记忆 | `tauri-plugin-window-state` | — |
| 文件打开靠 `fsRead` 手敲路径 | `tauri-plugin-dialog`（open/save） | 与右键菜单的「Open」配合 |
| 文件变动靠后端轮询/`fsChanged` | `tauri-plugin-fs` 的 watch，或继续用后端通知 | 后端已经会推 `fsChanged`，保持即可 |
| 无系统通知 | `tauri-plugin-notification` | 运行结束 / LSP 就绪时可选用 |
| HTML 菜单（`renderMenus`，PyCharm 风格） | **保留在 webview 里** | 不要同时上原生菜单，否则两套菜单会互相矛盾 |

## 8. 打包

```
npm run build:exe          # 现有：产出 Nolanguage.exe（Node SEA）
node scripts/build-frontend.mjs
cp dist/Nolanguage.exe src-tauri/binaries/Nolanguage-x86_64-pc-windows-msvc.exe
npm run tauri build        # 产出安装包 / 便携版
```

- Tauri 的 `externalBin` 要求 sidecar 文件名带 target triple 后缀，否则 `tauri build` 直接报错。
- 体积：Rust core 几 MB + Node SEA exe（现有体积）+ WebView2（Windows 10/11 系统自带，可作为可选依赖声明）。
- `--extension-host` 模式（`desktop/main.ts:57`）完全不受影响：扩展宿主仍是同一个 exe 的另一种 argv。
- **安装包需要联网**：WiX（MSI）与 NSIS 都是在打包阶段从 github.com 下载的，本机不可达 GitHub，
  因此只能产出二进制；`npm run tauri build` 需在有网环境执行。
- **`cargo build` ≠ 可运行产物**：它是 dev 构建（资产不嵌入、走 `devUrl`）。要么 `tauri dev` /
  `tauri build`，要么自己起 `scripts/serve-dist.mjs` 并把 sidecar 复制到 exe 旁边。

## 8.5 实施记录（2026-10-17）

### 实际编译结果

```
cargo check                  0 errors, 0 warnings
cargo clippy -- -D warnings  0 warnings
cargo build                  ~48s → target/debug/nolanguage.exe
tauri build                  release 二进制 → target/release/nolanguage.exe（已验证独立运行）
```

修掉的 4 个编译错误，全部落在设计文档预判的「plugin 引入方式 + async runtime」两类里：

| 错误 | 修法 |
| --- | --- |
| `E0603` ×2：`__cmd__engine_send` / `__tauri_command_name_engine_send` 是私有宏导入 | `#[macro_use] mod engine;` —— `#[tauri::command]` 的辅助宏生成在函数旁，glob `use` 不会再导出它们 |
| `E0425`：`generate_handler!` 找不到 `engine_send` | 宏通过 `#[macro_use]` 进来，但函数本身还要 `use engine::engine_send;` 并设为 `pub` |
| `E0599`：`AppHandle` 上没有 `manage` | `use tauri::Manager;`（在 `engine.rs`，不在 `lib.rs`） |
| `E0308`：`CommandChild::write` 期望 `&[u8]` | 传 `&line.into_bytes()` |

`rx.recv().await` **不需要** `ReceiverExt`——官方 v2 shell 示例就是直接调用，代码里加了注释说明
「若报方法缺失再加 import」作为兜底。

### 运行期发现（设计时未预料）

1. **fork 炸弹**：`sidecar("Nolanguage")` 的裸名回退在 NTFS 上解析到应用自身。这是本轮最严重的缺陷，
   修复方式是把「显式算路径 + 拒绝自 spawn」写进 `engine.rs`。
2. **`window.__TAURI__` 不存在**：只有 `__TAURI_INTERNALS__`。探测一个真实窗口才确认
   （`hasTauri: "undefined"`, `hasInternals: "object"`, `keys: ["plugins"]`, `invoke: "function"`）。
3. **`cargo build` 是 dev 构建**：窗口空白曾被误判为「Tauri 坏了」。
4. **`before*Command` 的 cwd 是仓库根**：第一次配成 `src-tauri/` 相对路径直接失败。
5. **单实例不是默认的**：不加 `tauri-plugin-single-instance`，双击两次就是两个窗口两个引擎——
   这正是用户报「程序重复启动」的另一种形态。

### 复现与验证手段

- `NOLANGUAGE_STDIO_TRACE=<file>`：引擎把每条入站/出站帧追加到文件。这是唯一能看见
  「UI 到底通过中继发了什么」的方法，上面 1/2 两个问题都靠它定位。
- `scripts/verify-transport.ts`：不依赖 Rust 也能证明两种传输可互换 + 真实引擎能在管道上对话。
- `scripts/verify-pycharm.ts` 的 `FakeTauri`：同一批 UI 断言在 IPC 宿主下重跑。

## 10. 风险与权衡

1. **引入 Rust**。这是最大的非技术权衡：项目现在是纯 TS + 零运行时依赖。Rust 只出现在构建期（`src-tauri/`），运行时仍是一个 exe + 一个 sidecar exe；但它确实带来第二种语言和工具链。缓解：Rust 侧刻意保持「不懂协议」，实际约 150 行。
2. **WebView2 仍是渲染引擎**。Windows 上 Tauri 用的就是系统 WebView2 —— 所以**UI 外观与今天完全一致**，这是好事（外壳不用改），但也意味着「换 Tauri」不会改善渲染兼容性。
3. **SEA exe 作为 sidecar 的体积**。引擎 exe 已经存在，Tauri 只是多带一个 Rust core（release 约 4.3 MB）。
4. **`node:sqlite` / `node:vm` 在 SEA 里的行为不变**，因为引擎还是同一个 Node 运行时 —— 零风险。
5. **调试链路变长**。从前端到引擎中间多一跳 Rust。缓解：`--panel-stdio` 模式可以脱离 Tauri 单独跑（阶段 1 就能测），Rust 只做转发，问题基本都在 TS 侧；再加 `NOLANGUAGE_STDIO_TRACE` 可直接看帧。
6. **两个宿主并存**。`npm run ide`（HTTP）与 Tauri 会长期共存，`Transport` 抽象必须保持干净，否则会退化成 `if (isTauri)` 散落各处。约束：判据只允许出现在 `BRIDGE` 与 `main()` 两处 —— 实施后确认仍只有这两处。
7. **外部下载依赖**。安装包打包阶段需要从 github.com 拉 WiX / NSIS；在无法访问 GitHub 的环境里
   只能拿到二进制。这是唯一无法用工程手段消除的依赖。

## 11. 结论

现在的 UI 用 Tauri 实现，本质是**换掉「窗口宿主 + 传输」两层，引擎原封不动**：

- 页面：`renderPyCharmHtml()` 的产物从「HTTP 响应」变成「Tauri bundle 资产」；
- 传输：WebSocket JSON 协议原样保留，从 ws 连接换成 `invoke`/`emit` 跨 IPC 到 sidecar 的 stdio；
- 窗口：从「借 Edge 的 Chromium 开关拼一个 app 窗口」换成 Tauri 原生窗口 + 插件；
- 测试：`FakeSocket` → `FakeTauri`，同一批 UI 断言双模式跑，证明迁移不改行为。

工作量集中在阶段 0–2（TS 侧抽象 + Rust 壳 ~150 行 + 前端落盘脚本）；引擎、协议、外壳 UI 三者都不需要重写。
