# 多语言调试适配方案

> 生成日期：2026-10-31
> 范围：`src/dap/`（DAP 客户端）、`src/panel/server.ts`（`handleDebug` / `handleDebugCmd`）、`builtin/*/manifest.json`、`examples/cpp@1.0.0`
> 相关文档：`docs/添加新语言指南.md` §5.1（面 7：调试）、`逻辑文档/20261021_PyCharm无感迁移优化方案.md`

---

## 0. 结论先说

调试的**引擎侧已经是语言无关的**：`DapClient` 只讲 DAP，`handleDebug` 里没有一条 `if (language === 'python')`。适配新语言在理想情况下**只需要往 manifest 加一个 `debug` 块**，零引擎改动——Python 与 Go 就是这么来的。

但**当前的 `launch` 载荷是「Python/Go 形状」的**：`handleDebug` 硬编码了 `{program, stopOnEntry, mode:'debug', args, env, cwd}`。这个形状对 debugpy / delve 够用，对其它适配器不够。所以「适配多语言」真正要做的是两件事：

1. **能声明的就声明**（加 `debug` 块）——已完成 90%；
2. **把硬编码的 launch 载荷模板化**（manifest 可声明 `launch` 模板 + 构建前置步骤）——这是剩下的 10%，也是多语言的真正门槛。

---

## 1. 现状：三层声明式架构

| 层 | 机制 | 配置位置 | 代码证据 |
|---|---|---|---|
| **① 发现** | `env 变量 → knownPaths（支持单段 glob）→ PATH` | `debug.discovery` | `src/langs/discover.ts` 的 `discoverBinary()` |
| **② 启动** | 拼命令 + `{resolved}` 替换，额外参数来自 `debug.args` | `debug.command` / `debug.args` | `server.ts` `handleDebug`：`head.replace('{resolved}', resolved.bin)` |
| **③ 会话** | 标准 DAP：initialize → launch → setBreakpoints → … | `debug.type`（`initialize.adapterID`，缺省用 `adapter`） | `src/dap/DapClient.ts` |

降级与提示也是声明式的：`degradedNote`（缺适配器时说什么）+ `install`（具体安装命令，见 2026-10-21 那次改动）。

**已声明 debug 的插件**

| 插件 | adapter | type | command | 备注 |
|---|---|---|---|---|
| `builtin/python@1.0.0` | `debugpy` | `python` | `["{resolved}"]` | `install: pip install debugpy` |
| `builtin/go@1.0.0` | `delve` | `go` | `["{resolved}","dap"]` | dlv 需要 `dap` 子命令 |
| `examples/cpp@1.0.0` | `codelldb` | `cppdbg` | `["{resolved}","--port","0"]` | 编译型，见 §4.2 |

**尚未声明**：`builtin/javascript@1.0.0`（顶层键只有 file/grammar/lsp/run）、`builtin/markdown@1.0.0`。

## 2. 适配一门新语言：最小步骤

按 `docs/添加新语言指南.md` §5.1，往 manifest 加：

```jsonc
"debug": {
  "adapter": "<id>",                  // 展示/日志用
  "type": "<dap type>",               // initialize.adapterID，缺省 = adapter
  "discovery": {
    "commands": ["<cmd>"],            // PATH 里找
    "envVars": ["<ENV>"],             // 优先级最高：多工具链机器的逃生口
    "knownPaths": ["~/...", "C:/..."] // 支持单段 * glob
  },
  "command": ["{resolved}"],          // 无 {resolved} 时视为绝对路径，可省 discovery
  "args": [],                         // 追加在 command 之后（--listen 类适配器）
  "serverName": "<显示名>",
  "memoryHint": "80MB",
  "degradedNote": "<缺适配器时说什么>",
  "install": "<具体安装命令>"         // 缺适配器时直接给用户可执行命令
}
```

发现失败时 `handleDebug` 回 `ok:false` + `error(degradedNote)` + `hint` + `install`，客户端弹「Debug unavailable」并打印安装命令——**不需要为新语言写任何 UI 代码**。

## 3. 各语言适配器速查

| 语言 | 适配器 | `type` | 启动形态 | launch 关键字段 |
|---|---|---|---|---|
| Python | debugpy | `python` | `debugpy-adapter` | `program` / `module`、`args`、`env`、`cwd`、`stopOnEntry` |
| Go | delve | `go` | `dlv dap` | `program`、`mode:debug\|test`、`args`、`env`、`cwd` |
| JS / TS | js-debug（vscode-js-debug）或 `node --inspect` | `node` / `pwa-node` | `js-debug-src`/`node` | `program`、`runtimeExecutable`、`args`、`cwd`、**`sourceMaps`**、`outFiles` |
| C / C++ | codelldb | `cppdbg` / `lldb` | `codelldb --port 0` | `program`(**二进制**)、`MIMode`、`miDebuggerPath`、`sourceFileMap` |
| Rust | codelldb 或 `lldb-dap` | `lldb` / `rust` | 同上 | `program`(= target/debug/xxx)、`sourceLanguages:["rust"]` |
| Java | java-debug（LSP4J Debug） | `java` | `com.microsoft.java.debug.plugin` 启动脚本 | `mainClass`、`classPaths`、`modulePaths`、`projectName` |
| PHP | xdebug | `php` | 无独立适配器（需 `php-debug` 适配层） | `program`、`runtimeArgs`、**`port`（attach 风格）** |
| Ruby | rdbg（`debug` gem） | `ruby` | `rdbg --open` | `program`、`command`(script)、`useBundler` |

> 注意 **JS 的特殊性**：`builtin/javascript@1.0.0` 的 `run.mode` 是 `inline-vm`（页面内嵌 VM）。内嵌 VM **无法挂调试器**——要调试 JS 必须改走真实 `node` 进程（`runtimeExecutable`），这是运行模式的调整，不只是加 debug 块。

## 4. 当前架构的 5 个缺口（按重要性）

### 4.1 launch 载荷硬编码（最关键，P0）

`handleDebug` 现在构造：

```
{ program, stopOnEntry, mode: 'debug', ...(args), ...(env), ...(cwd) }
```

问题：`mode:'debug'` 是 **dlv 方言**（debugpy 忽略它，但别的适配器可能把 `mode` 理解成别的意思）；Java 需要 `mainClass`，cppdbg 需要 `MIMode`，Node 需要 `runtimeExecutable`——全都传不进去。

**建议**：manifest 增加 `launch` 模板，引擎只做占位符替换：

```jsonc
"debug": {
  ...,
  "launch": {
    "program": "{program}",
    "stopOnEntry": "{stopOnEntry}",
    "cwd": "{cwd}",
    "args": "{args}",
    "env": "{env}",
    // 适配器私有的静态字段原样透传
    "static": { "mode": "debug", "MIMode": "lldb" }
  }
}
```

占位符：`{program}` `{file}` `{workdir}` `{cwd}` `{args}` `{env}` `{stopOnEntry}` `{port}`。
缺省（不写 `launch`）保持今天的行为 → 现有 Python/Go 零改动。**工期 ~1 天。**

### 4.2 调试前没有构建步骤（编译型语言的硬门槛，P0）

`run` 有 `steps[role=build]`（cpp 例子：`g++ -std=c++17 -O0 "{file}" -o "{workdir}/nl_main{exe}"`），但 `handleDebug` **没有任何构建步骤**，`program` 直接取配置的 `path`。对 C/C++/Rust 这意味着拿**源文件**去喂调试器——必然失败。

**建议**：`debug` 增加 `preLaunch`（复用 run 的 step 语法，通常带 `-g`/`-O0`）：

```jsonc
"debug": {
  ...,
  "preLaunch": {
    "cmd": "\"{toolchain}\" -std=c++17 -g -O0 \"{file}\" -o \"{workdir}/nl_dbg{exe}\"",
    "timeoutMs": 60000
  },
  "program": "{workdir}/nl_dbg{exe}"   // 调试目标不再是源文件
}
```

引擎侧：在 `dap.start()` 之前跑该命令，失败则回 `ok:false` + 编译输出。**工期 ~1 天。**

### 4.3 源码路径映射（P1）

TS/JS 的 `sourceMaps`、cppdbg 的 `sourceFileMap`、容器的 `localRoot/remoteRoot`。没有它，断点会落在生成文件上或根本不命中。

**建议**：并入 §4.1 的 `launch.static` + 占位符 `{workdir}` 即可覆盖大半；真正的 remote/容器映射留到有需求再做。**工期 0.5 天（随 4.1）。**

### 4.4 attach 未实现（P1）

目前 `request:'attach'` **被当作 launch 处理**（`server.ts` 注释已声明）。PHP/xdebug、以及"附加到已运行进程"都需要 attach。

**建议**：manifest 声明 `supportsAttach: true`；客户端配置里 `request:'attach'` 时，引擎发 DAP `attach` 请求并带 `port`/`host`/`processId`。**工期 1–2 天。**

### 4.5 断点与能力协商的细节（P2）

- **断点校验**：部分适配器在 `setBreakpoints` 回包里把未命中的行标为 `verified:false`（如 TS 未生成 sourcemap）。现在客户端不回读，用户看到红点但不会停。
- **行列基准**：`linesStartAt1` / `columnsStartAt1` 来自 `initialize` 能力；目前按 1-based 硬假设。
- **`stopOnEntry`**：并非所有适配器都支持。

**建议**：`setBreakpoints` 回包后把未 verified 的行回传，UI 把圆点改为空心。**工期 1 天。**

## 5. 实施路线

| 优先级 | 项 | 工期 | 依赖 |
|---|---|---|---|
| **P0** | `debug.launch` 模板（占位符 + 静态字段） | 1 天 | 无，向后兼容 |
| **P0** | `debug.preLaunch` 构建步骤 + `program` 模板 | 1 天 | 复用 run 的 step 语法 |
| **P1** | JS/TS 接入（改走真实 node + sourcemaps） | 2–3 天 | P0 + 运行模式调整 |
| **P1** | C/C++ 跑通（codelldb + 带 -g 构建） | 1–2 天 | P0（4.2 是硬门槛） |
| **P1** | attach 支持 | 1–2 天 | 4.1 |
| **P2** | 断点 verified 回传 / 行列基准 | 1 天 | 4.1 |

**P0 共约 2 天**，做完之后「加一门语言的调试」才真正退化成**只写 JSON**。

## 6. 验收清单

1. 给一个新语言只加 `debug` 块（不改引擎 TS），`startDebugSession` 能启动适配器并停在第 1 行。
2. C/C++：`preLaunch` 用 `-g -O0` 产出二进制，调试器停在**源码行**而非汇编/生成文件。
3. JS/TS：源码 `.ts` 上打断点，命中经 sourcemap 映射后的运行时位置。
4. 缺适配器时：控制台与弹窗给出**该语言自己的** `install` 命令（非通用文案）。
5. 适配器启动失败（非缺失）：回 `ok:false` + 适配器 stderr，不静默。
6. `attach` 能连上已运行进程；不支持 attach 的适配器在 UI 上明确标注。
7. 回归：`verify-dap` 21/21、`verify-pycharm` 全绿、`verify-langplugins` 通过（manifest 校验）。

---

## 7. 一句话总结

**调试的引擎已经是语言无关的，多语言适配 90% 是 manifest 的事**；剩下的 10% 是把 `handleDebug` 里那条硬编码的「Python/Go 形状」launch 载荷换成**可声明的模板**，并补上**编译型语言的调试前构建**。这两件（约 2 天）做完，加一门语言的调试就只剩写 JSON。
